## 关键发现(给 AI 自己看,防失忆)

### ReAct 循环骨架的核心结构

- **Execute 入口**(engine.go:206):装配 state/systemPrompt/messages/tools 4 样,开 Langfuse top-level span,调 executeLoop
- **executeLoop 主循环**(engine.go:362):for CurrentRound < MaxIterations(默认 20),3 种 iterOutcome(next/continue/break)switch 控制,defer emitCompletion 保证 exactly-one 完成事件,ctx 取消 salvage 路径(有 tool 结果时合成答案)
- **runReActIteration 一轮 4 步**(engine.go:468):
  - Step 0 manageContextWindow(笔记 27 的 4 道闸,token 估算用 lastUsage+delta 优化)
  - Step 1 Think callLLMWithRetry(下篇深挖)
  - Step 1.5 stuck loop 检测(连续 2 轮相同内容无 tool_call 强停,防 unhandled finish reason)
  - Step 1.6 ctx 取消保 partial step(用户按 stop 时保留半截思考,不设 IsComplete)
  - Step 2 Analyze analyzeResponse(content_filter / natural stop 无 tool_call → done;emptyContent 重试 2 次 nudge,再失败 fallback)
  - Step 3 Act executeToolCalls(下篇深挖)
  - Step 4 Observe appendToolResults(OpenAI 格式 assistant 带 tool_calls + tool 带 ToolCallID 配对不拆)

### 3 种 iterOutcome 的精确语义

- **next**:advance CurrentRound,正常一轮结束进下一轮
- **continue**:不 advance 重跑本轮(empty retry 用,LLM 答空白时重试,不算一轮)
- **break**:退出循环(自然停/final answer/stuck loop/content_filter/ctx 取消保 partial)

### 4 类异常路径

| 异常 | 触发 | 是否重试 | 是否保产出 | 退出方式 |
|---|---|---|---|---|
| ctx 取消 | 用户操作 | 否 | 是(salvage/partial) | return ctx.Err() / break |
| stuck loop | 连续 2 轮相同 | 否 | 是(重复内容当答案) | break |
| empty retry | natural stop + empty | 是(≤2 次) | 重试成功保内容,失败用 fallback | continue / break |
| content_filter | finish_reason | 否 | 是(内容或 fallback) | break |

### 兜底机制

- **handleMaxIterations**(finalize.go:166):跑满 20 轮没 natural stop 时调 streamFinalAnswerToEventBus 合成,失败用 fallback 文本,总是设 IsComplete=true
- **ctx 取消时不跑 handleMaxIterations**(engine.go:439 `ctx.Err() == nil`):防 fallback 文本泄露到 UI 让用户困惑("我都喊停了你还在答")
- **streamFinalAnswerToEventBus**(finalize.go:27):把所有 tool 结果作为 user 消息(不是 tool 消息,独立 LLM 调用不需要配对协议)+ final prompt,独立 LLM 调用合成,Thinking disabled,Temperature 0.7
- **emitCompletionEvent**(finalize.go:187):写 state.RoundSteps 进 EventAgentComplete 事件,handler 持久化到 Message.AgentSteps,LoadAgentHistory 下次读

### token 估算优化(engine.go:196)

- 有 lastUsage(API 返回的精确 token)时:用 lastUsage.TotalTokens 作基线 + 只 BPE 估算 delta(新增消息),避免全量估算
- 条件 `lastSentMsgCount < len(messages)`:messages 被 manageContextWindow 压缩变短时走全量估算
- lastSentMsgCount 在 Step 1 调 LLM 前赋值(engine.go:550),lastUsage 在 LLM 返回 usage 时赋值(engine.go:560)

### 跟笔记 27 4 道闸的衔接

- 闸② redact 在 buildMessagesWithLLMContext 跑一次(装配阶段),不在 manageContextWindow 里
- 闸① trim/闸③ Consolidator/闸④ Compress 在 manageContextWindow 里每 round 跑
- appendToolResults 的输出是下一轮 trim 的输入(循环关系)

### 跟 KnowledgeQA 的对比

- 单轮单次(无循环) vs 多轮 ReAct(for 循环 20 轮)
- 无 4 道闸 vs 有 4 道闸
- 无异常路径 vs 4 类异常路径
- 生成完就 done vs 多种终态判断
- KnowledgeQA 牺牲多步推理换简单,Agent 用复杂度换多步推理

### 跟 claude-code 的对比(DB-centered vs in-memory state,设计哲学差异)

用户问"WeKnora 跨轮记忆用 DB 代替内存,跟 claude-code 差异在哪",我读了 claude-code 源码(`D:/GoProject/claude-code`)对比:

**WeKnora = DB-centered(数据库中心化)**:
- AgentEngine 是 per-turn 实例(每次提问新建销毁),内存里啥都不存
- 跨 turn 记忆全在 DB messages 表,每次提问从 DB 读历史(`LoadAgentHistory`)
- 4 道闸是视图层(只改发给 LLM 的 messages,不动 DB 原版)
- 不需要冻结决策(DB 不变 + 算法确定 → 字节天然一致,靠架构保字节稳定)
- 比喻:每次提问翻账本,看完合上,账本一字不改

**claude-code = in-memory state(内存状态)**:
- state.messages 是 React useState 维护的内存数组(`REPL.tsx:1182`),整个 session 活着,不是每次提问重建
- 每轮往内存数组尾部 push,越攒越长
- DB(JSONL 文件 `sessionStorage.ts:1128 appendEntry`)只做备份(防崩溃恢复),不是主角
- 压缩是破坏性改 state.messages(microcompact 把旧 tool_result 换成 `TIME_BASED_MC_CLEARED_MESSAGE = '[Old tool result cleared]'` `microCompact.ts:36`)
- 需要冻结决策(`ContentReplacementState` `toolResultStorage.ts:390`:seenIds Set + replacements Map)保字节一致保 prompt cache 命中——每个 tool_result 贴标签记"已经压成啥了",下次直接拿标签内容,不重新压缩
- 比喻:活账本上直接划,划掉就没了,给每笔账贴标签记"已经划成啥了"防下次划不一样

**最根本差异(设计哲学)**:
- WeKnora 牺牲性能换简单和完整(DB 是主角,视图层随便改,改坏了从 DB 重读)
- claude-code 牺牲复杂度换性能和省 token(内存里直接改,快,但需要冻结决策兜底)
- 不仅是"存哪里"的差异,是整个系统设计哲学的差异

**关键代码位置(claude-code 侧)**:
- state.messages 内存数组:`REPL.tsx:1182`
- query loop state:`query.ts:204`(`messages: Message[]` 是 State 字段)
- appendEntry 异步写盘:`sessionStorage.ts:1128`
- ContentReplacementState(冻结决策):`toolResultStorage.ts:390`
- TIME_BASED_MC_CLEARED_MESSAGE(占位符):`microCompact.ts:36`
