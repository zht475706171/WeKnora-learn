## 关键发现(给 AI 自己看,防失忆)

### Approval 闸核心结构

- **`Gate`**(approval/gate.go:135):管所有等待中的审批,pending map 按 pendingID 索引 waiter
- **`waiter`**(gate.go:144):ch(带 1 缓冲)+ tenantID/userID + once(防重复)+ resolved(原子)
- **`Decision`**(gate.go:76):4 种状态(同意/拒绝+原因/超时/ctx 取消),ModifiedArgs 同意但改参数
- 4 个核心函数:NeedsApproval/RequestAndWait/Resolve/RequestOAuthAndWait

### `NeedsApproval` fail-close 设计(gate.go:289)

- 查 checker.IsRequired 失败时,默认**要审**(failClose=true),不放行
- 审批是安全功能,查不了宁可多审一次,不能漏放危险工具
- 可通过 `WEKNORA_AGENT_TOOL_APPROVAL_FAIL_OPEN=true` 改放行模式(legacy 行为)

### `RequestAndWait` 7 步 + select 三路(gate.go:309)

```
Step 1: 生成 pendingID(uuid)
Step 2: 建 waiter,放进 g.pending map
Step 3: defer 从 map 删 pendingID(防泄漏)
Step 4: 发 EventToolApprovalRequired 事件(前端弹框)
Step 5: 起 timer(10 分钟超时)
Step 6: select 三路(用户决议/超时/ctx 取消)
Step 7: emitResolved(用 context.WithoutCancel 保证 ctx 取消也能发事件)
```

**select 三路**:
- 路径 A 用户决议:Resolve 调 w.deliver,决议写入 ch
- 路径 B 超时:自己构造"拒绝+超时"决议,自己 deliver(占住 Once 防后续 Resolve 再投),再 <-w.ch 读出来
- 路径 C ctx 取消:自己构造"拒绝+取消"决议,同上

**为什么超时和取消要自己 deliver 再 <-w.ch**:
- deliver 用 sync.Once 保证只发一次,超时先发了,后续用户点同意不会再进 ch
- deliver 后还要 <-w.ch 消费掉,才能 return

**emitResolved 用 context.WithoutCancel**:即使 ctx 已取消(用户按 stop),也要发"审批结束"事件给前端清理弹框

### `Resolve` 三路分支 + 跨实例(gate.go:539)

```
Resolve:
  deliverLocal → 成功:返回 nil
              → ErrTenantMismatch/ErrUserMismatch/ErrAlreadyResolved:返回错误
              → ErrPendingNotFound:
                  rdb == nil:返回错误(真找不到)
                  rdb != nil:走 resolveCrossInstance(跨实例找)
```

**deliverLocal 三层校验**(gate.go:638):
1. pendingID 存在:本实例有这个等待者
2. 租户匹配:防跨租户越权
3. 用户匹配:防 A 用户决议 B 用户的审批(空 caller userID 也算 mismatch,fail-close)

### `resolveCrossInstance` 跨实例流程(gate.go:565)

1. 副本 A 收到 Resolve,本地找不到(ErrPendingNotFound)
2. 副本 A 订阅专用回复频道 `reply:<pendingID>`
3. 副本 A 发决议到主频道,带 ReplyChannel/OriginID/RequestNonce
4. 副本 B(等待者所在实例)订阅主频道,收到决议(跳过 OriginID == instanceID 的自己发的),本地 deliverLocal,根据结果往回复频道发 ack(带状态码 ok/tenant_mismatch/user_mismatch/already_resolved/not_found)
5. 副本 A 从回复频道收 ack,RequestNonce 匹配才消费(防并发串 ack),根据状态码返回 HTTP 响应(3 秒超时,超时返回 ErrPendingNotFound)

### 三个关键设计

**① instanceID 防自处理**:每个实例进程启动生成 uuid,收到自己发的消息跳过(防本地噪音)
**② RequestNonce 防并发串 ack**:同一 pendingID 多个并发 Resolve(用户抖动重试),每个用唯一 nonce,ack 带回 nonce,只有匹配的 Resolve 才消费
**③ ReplyChannel per-pending**:`reply:<pendingID>` 专用,不共用,防不同 pending 的 ack 串

### `runSubscriber` 订阅 + 指数退避重连(gate.go:212)

- 每个实例启动一个 goroutine 订阅主频道,生命周期同进程
- 收到跨实例决议:跳过自己发的,deliverLocal,根据 err 回 ack
- Redis 断了指数退避重连(1s/2s/4s/.../30s 封顶),订阅成功重置 backoff

### `RequestOAuthAndWait` 变体(gate.go:428)

- 跟 RequestAndWait 区别:不查 checker(reactively 由 transport 错误驱动,不是预先配置)/事件类型不同(EventMCPOAuthRequired)/授权完成则重试工具调用/WaitTimeout 可配
- 触发场景:MCP 服务返回"要 OAuth 授权"(用户没登过 GitHub),弹窗让用户授权,授权完重试

### 跟 mcp_tool.go 的衔接(mcp_tool.go:116-183)

- `MCPTool.Execute` 里,`gate.NeedsApproval` 判断要审
- **关键 1**:`waitCtx = meta.ApprovalCtx`(不带 60s 工具超时,防审批被打断)
- `gate.RequestAndWait(waitCtx, ...)` 阻塞等
- 同意但改参数:`args = decision.ModifiedArgs`
- **关键 2**:审批后重新派生 fresh ctx:从 ApprovalCtx 派生带 ExecTimeout 的新 ctx,给真正 MCP CallTool 完整超时窗口
- 两个关键设计都接笔记 30 的 ApprovalCtx 不带工具超时

### 完整例子流程(delete_repo)

```
1. runReActIteration Step 3 → executeToolCalls → runToolCall
2. runToolCall Step 11 → toolRegistry.ExecuteTool → MCPTool.Execute
3. MCPTool.Execute:
   a. gate.NeedsApproval → true
   b. waitCtx = meta.ApprovalCtx(不带 60s)
   c. gate.RequestAndWait(waitCtx, ...)
      - 生成 pendingID
      - 发 EventToolApprovalRequired 事件(前端弹框)
      - select 三路等待
4. 用户点"同意"(不改参数)
   - 前端调 POST /api/agent/approval/resolve
   - 后端调 gate.Resolve(tenantID, userID, pendingID, Decision{Approved: true})
   - deliverLocal → w.deliver → ch
5. RequestAndWait 路径 A 触发,d = <-w.ch,return Decision{Approved: true}
6. MCPTool.Execute 收到 Approved == true
   - 不改参数
   - 重新派生 fresh ctx(从 ApprovalCtx 派生带 60s)
   - connectAndCall(freshCtx)
7. MCP CallTool 执行 delete_repo
8. 结果返回模型,继续 ReAct
```

异常路径:
- 超时(10 分钟):路径 B,返回 ToolResult{Success: false, Error: "approval timeout"}
- 用户按 stop:路径 C,返回"拒绝+取消"
- 多副本:副本 A Resolve 找不到 → 跨实例 Pub/Sub → 副本 B 交付 → 回 ack → 副本 A 返回 200

### 跟 Think/Act 对比

| 维度 | Think | Act | Approval |
|---|---|---|---|
| 阻塞性 | 流式不阻塞 | 工具执行阻塞有超时 | 人审阻塞可达 10 分钟 |
| 超时 | 120s chunk 间 | 60s 工具执行 | 10 分钟审批 |
| 重试 | 2 次退避 | 无 | 无(等一次决议) |
| 取消 | ctx 取消保 partial | ctx 取消返回错误 | ctx 取消返回"拒绝+取消" |
| 跨实例 | 不涉及 | 不涉及 | Redis Pub/Sub |
| 决议来源 | 模型输出 | 工具返回 | 用户点击 |

设计哲学:Think 跟模型对话(快)/Act 干活(中等)/Approval 等人(很久,跨实例,需要 Pub/Sub)
