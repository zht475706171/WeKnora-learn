### 分流点(handler/session/qa.go:843-877)
- 判断:`customAgent.IsAgentMode()` 优先 > `request.AgentEnabled`

### 为什么分两条路径
- 回答哲学不同:KnowledgeQA 固定 RAG 单轮单次(代码控制检索)/ Agent LLM 自主决策工具循环多轮多步(LLM 控制检索)
- 历史结构不兼容:KnowledgeQA 一轮 2 条 / Agent 一轮 N 条(tool 消息)
- 检索控制权相反:KnowledgeQA 代码先检索 / Agent LLM tool_call 触发
- token 增长模式不同:KnowledgeQA 靠 maxRounds 硬兜 / Agent 需运行时压缩闸
- 存表同(messages)读写不同:KnowledgeQA 写 RenderedContent+空 AgentSteps / Agent 写 AgentSteps+不写 RenderedContent

### Agent 路径载入历史(LoadAgentHistory agent_history.go:50)
- fetch 余量更大:maxRounds*4 下限 50(vs KnowledgeQA maxRounds*2+10)
- 丢 RenderedContent 方式不同:KnowledgeQA 显式丢 / Agent 直接不读该字段
- ★展开 AgentSteps:每个 step 非终结 tool_call 展开成 assistant(tool_calls)+tool(每条),最后补 assistant(最终答案)
- filterNonTerminalToolCalls:滤掉 legacy final_answer 和 pipeline 伪 tool_call(代码调的不是 LLM 调的)

### 关键发现补充

#### Q1 trim 的 3 个盲区
- **单工具无限制**:currentTurnToolResultBudget 只判断总和,单个工具多大都行(只要总和没超)。盲区:单工具 31K 占满 budget 97% 推理空间被压
- **为什么没单工具限制**(推断):①工具实现层应自做体积控制(Read maxTokens/Bash 截 stdout)trim 是事后兜底 ②加单工具限制触发后只能压缩或丢弃,后者破配对
- **渐进式塞满**:10 个工具各 10K 场景,trim 会塞满 32K budget(最新3条原文+1条头尾预览+6条marker),保证≤budget 不保证留推理空间
- **头尾预览丢中间**:1:3 比例基于"工具结果信息分布不均(头上下文/尾关键/中间冗余)"假设。marker 明说"Re-run the tool"暗示 LLM 重查兜底。盲区:不可重调工具(一次性副作用/时间敏感)中间丢了永久丢,trim 没区分可重调/不可重调

#### Q2 prompt cache 策略——不显式管理,靠架构间接保证
- **Agent 引擎不维护 cache**(engine.go:33 注释明说),无等价 claude-code ContentReplacementState 的 seenIds/replacements Map
- **3 个间接机制**:
  1. DB 是 single source of truth,LoadAgentHistory 每次从 DB 重新载入,算法确定性→视图天然字节一致
  2. 工具注册顺序稳定(registry.go:90 注释"reshuffle tools block break cache")
  3. 视图层拷贝不原地改 + 算法确定性
- **Consolidator 的 cache 漏洞**:manageContextWindow 返回的 messages 只用于本次 LLM 调用(engine.go:534)不写回 DB。下一轮再从 DB 载入再跑,Consolidator 反复触发会重新调 LLM 摘要同样旧历史,LLM 非确定性(Temperature 0.3)→ summary 字节变了→后面所有消息 cache 失效
- **WeKnora 接受这个代价**:Consolidator 触发频率低(token>0.5),cache 失效代价 < 摘要节省 token 代价
- **跟 claude-code 根本差异**:claude-code in-memory state + 显式决策冻结 / WeKnora DB-centered + 不显式管理。架构层取舍:WeKnora 选简单性放弃极致 cache 命中率

#### Q3 Consolidator 摘要 prompt 翻译
- **user prompt**(buildConsolidationPrompt consolidator.go:253):4 个保留点(关键事实和决策/工具执行结果/用户原始意图/错误和修复)+ 格式化对话为 `**User**/**Assistant** [called tools:X]/**Tool [name]**` 纯文本,每条预截断(user/assistant 2000 字符,tool 1000 字符)
- **system prompt**(consolidationSystemPrompt consolidator.go:326):6 条要求(同语言/保留事实数字细节/包含工具产出/注明错误/多主题分章节/30% 以下)+ "只输出总结不要前言"
- **落盘格式**:`[Memory Summary - N earlier messages consolidated]\n\n<summary>`,system role,插在 system 之后保留历史之前
- **失败兜底 rawArchive**:每条截 500 字符机械拼接,非 LLM 摘要,语义损失大但保底

#### Q4 CompressContext 讲透
- **跟 Consolidator 关系**:先礼后兵。Consolidator 0.5 触发 LLM 摘要,CompressContext 0.8 触发硬砍。正常 Consolidator 降到 0.3 离 0.8 远不触发,极端情况(Consolidator 摘要后当前轮 tool 暴涨)才两道都触发
- **触发**:token > MaxContextTokens * 0.8(默认 16 万)
- **算法 6 步**:切三段(system/history/tail)→ groupToolMessages 分组(assistant tool_calls + 后续连续 tool 一组,配对不拆)→ 算 tokensToFree → 从最旧 group 砍到够为止 → 组装 [system]+[砍点后 groups]+[tail] → 返回
- **关键**:只砍够砍的最旧几个 group,按 group 砍会多砍(整组砍不能砍半个)
- **跟 Consolidator 分组形态像用途反**:findKeepBoundary 从最新往前数保留 / groupToolMessages 从最旧开始砍
- **worked example**:11 条 messages 当前 37700 超 32000 阈值 5700,砍 group 0(500)+group 1(12300)=12800≥5700 停,多砍 7100,降到 24900(0.62)
- **极端场景**:两道闸都触发时 CompressContext 可能砍掉 Consolidator 生成的 [Memory Summary] 消息,等于白摘要
- **设计哲学**:保 system+当前轮/保配对/从最旧砍/多砍不多留/零成本兜底

#### Q1 答案:stable prefix 不需要引入冻结决策,对话历史不建议引入
- **stable prefix 段**:已天然字节一致(同 session 同 agent 同 KB 同记忆),不需要引入。唯一破坏因子是 summary 进 prefix,单点改可解决(改 PromptPrefixFingerprint 只取第一条 system,或把 summary 改 user role)

#### Q2 答案:用户理解精确化后对,推荐 Consolidator 摘要落盘

- 精确版:stable prefix 命中(没触发 Consolidator)/ 对话历史基本失效 / 触发 Consolidator 后整个 prefix 也失效
- 3 个优化方向:方向 1 摘要落盘(推荐,小改不动架构)/ 方向 2 Temperature 调 0(中改,可叠加)/ 方向 3 引入 in-memory state(大改,不建议)

#### Q3 答案:现状没有后台/定时摘要机制,每次 Consolidator 重调 LLM

- 完整方案 A/B/C/D:摘要落盘 → 查表复用 → 增量摘要 → CompressContext 优先保留 summary

#### 三问收敛到同一优化方向

### 用户原始需求

### 关键发现补充(第四轮)

#### 两个层面拆分(核心更正)
- **层面 A:token 超了,要不要压缩**(生存问题)——不该管 cache,命都保不住了
- **层面 B:不压缩时,怎么保 cache 命中**(效率问题)——管的就是 cache
- 之前把两个层面混在一起,把"压缩的必然物理后果"当成"stable prefix 机制隐患"——表述失误
- 触发压缩时 cache 失效是物理后果,不是机制问题

#### claude-code vs WeKnora 精确对比(4 个新维度)
| 维度 | claude-code | WeKnora |
|---|---|---|
| 历史非 KB 工具结果 | 压缩+冻结决策保住小体积 | 不压缩(每轮从 DB 读原版全量) |
| 当前轮工具结果 | per-message 预算全压 | 只压总和 ≤32K,单工具可 31K |
| 压缩触发时机 | 晚(历史保持小体积,token 涨慢) | 早(历史全量,token 涨快) |
| cache 命中率(百分比) | 历史段命中率本身两者差不多 | miss 部分(当前轮)更大,百分比可能更低 |
| 实际省的算力 | 多(总 token 小,绝对省算力多) | 少(历史大,绝对费算力多) |

#### 冻结决策的真正价值(关键澄清)
- 不是"让 cache 命中"——WeKnora 靠 DB 原版+算法确定也能命中历史段 cache
- 是"让压缩后的历史保持小体积"——省 token 关键,压缩触发晚的根因
- 保住的是"压缩成果",不是"cache 命中"
- claude-code 需要它是因为 in-memory state 视图层重新生成可能字节不同;WeKnora 不需要是因为 DB-centered 已保证

#### 冻结决策解决不了 summary 字节变的问题
- summary 字节变是"源头问题"(LLM 非确定性),不是"被改问题"
- 冻结决策是给"会被改的消息"用的——检测"被改"事件,记映射,按映射还原
- summary 没被改,是每次调 LLM 重新生成字节就不同——冻结决策检测不到"被改"事件,根本不触发
- 解法是"摘要落盘复用"(下次不调 LLM,直接读上次的 summary),不是冻结决策

#### 摘要落盘优化方向重新定位
- 主价值:省 LLM 调用(层面 A 成本优化)
- 顺带好处:cache 命中率提升(层面 B 副作用收益)
- 不是"保 cache"的优化——触发压缩时 cache 失效是必然物理后果,顺带收益边际
- 去掉"把 summary 排出 prefix 段"——性价比低,触发压缩占比少,改指纹逻辑有复杂度有风险
