## 关键发现(给 AI 自己看,防失忆)

### Act 阶段 4 函数定位

- **`executeToolCalls`(act.go:217)**:外层入口,看 ParallelToolCalls && n>=2 决定走并行还是串行
- **`executeToolCallsParallel`(act.go:242)**:errgroup 并发,按原序收集,不连坐
- **`executeSingleToolCall`(act.go:310)**:for 循环串行,跑完立刻推事件
- **`runToolCall`(act.go:356)**:核心 13 步,串并行都用它
- 比喻:调度员(executeToolCalls)/两种施工模式(并行/串行)/单个工人(runToolCall)/翻译(formatToolHint)

### `executeToolCallsParallel` 三个关键设计

1. **`i, tc := i, tc` 捕获循环变量**:Go 闭包经典坑,显式拷贝防串号
2. **`results[i] = toolCall` 按原序写入**:并行完成顺序乱,但结果按模型发起顺序存,前端展示一致
3. **`return nil` 不取消兄弟任务**:工具之间独立,一个失败不该连累其他(errgroup 默认会取消)

### `runToolCall` 13 步流程

```
Step 1:  NormalizeToolCallID 规范化 ID
Step 2:  json.Unmarshal 解析参数
Step 3:  失败 → RepairJSON 修复 → 再解析 → 再失败返回错误给模型(加"换思路"提示)
Step 4:  formatToolHint 生成 UI 提示
Step 5:  发 EventAgentToolCall 事件
Step 6:  PipelineInfo 日志
Step 7:  开 langfuse span(buildToolSpanInput 双层记录)
Step 8:  取 principal + 设 execTimeout
Step 9:  装 ToolExecContext(ApprovalCtx 用 toolCtx 不带工具超时)
Step 10: 查 UnresolvedHandles → 有就拒绝执行
Step 11: context.WithTimeout → toolRegistry.ExecuteTool → toolCancel
Step 12: 装结果 ToolCall{...}
Step 13: finishToolSpan + 三级 PipelineInfo/Warn/Error 日志
```

### JSON 修复两层兜底

- 模型输出残缺 JSON 很常见(漏逗号/引号不配对/尾随逗号)
- 第一层:`json.Unmarshal` 直接解析,成功就用
- 第二层:失败调 `RepairJSON` 修复后解析
- 还失败:返回错误给模型,末尾加 `[Analyze the error above and try a different approach.]`
- 修复成功:重新走 `modelContext.DecodeToolCalls` 解析临时句柄(cN/dN/bN/wN/iN/res://)

### `toolExecutionTimeout` 分流(const.go:49)

- 大部分工具:`defaultToolExecTimeout = 60s`
- `shell_exec`:`shellExecToolTimeout = 10m5s`(用户跑长时间命令不该被打断)
- 按工具名分流,不是统一超时

### ApprovalCtx 不带工具超时的设计

- `ToolExecContext.ApprovalCtx` 用 `toolCtx`(round 级 ctx),不用 `toolExecCtx`(带 60s 超时)
- **为什么**:MCP 工具的人审闸(人审批)可能要几分钟,60s 超时会打断审批
- `ExecTimeout` 还是 60s,工具本身执行 60s 超时,但审批等待不算在 60s 内
- 这是为 Approval 闸(下篇深挖)留的后门

### UnresolvedHandles 严格拒绝

- 未解析的模型句柄(cN/dN/bN/wN/iN/res:// 等临时引用)绝不能进工具执行
- **为什么**:这些是"临时引用",不是真实 ID,幻觉或过期句柄进数据库/外部服务有安全风险
- 设计哲学:执行前最后一道防线拦截,而不是执行后回滚

### formatToolHint UI 提示

- `toolDisplayNames` map:19 个工具的内部名 → 中文显示名映射
- `toolHintSensitiveArgs`:只有 `database_query` 敏感(SQL 暴露实现细节)
- 三个例子:
  - `web_search` + `{"query": "腾讯"}` → `搜索网页("腾讯")`
  - `knowledge_search` + 长查询 → `知识搜索("长查询…")` (截断 40 字)
  - `database_query` + SQL → `查询数据` (只显示名字,不展示 SQL)

### langfuse span 双层记录

- `buildToolSpanInput` 记 `model_arguments`(模型原始输出)和 `resolved_arguments`(解析后真实执行参数)两边
- `argument_resolution` 字段记参数解析方式(modelcontext.ArgumentResolutionUnchanged 等)
- 敏感工具(database_query)的 span 输入也脱敏(只记 key 不记值,`args_redacted: true`)
- `finishToolSpan` 错误分类:execErr != nil 是执行错误;Result.Success == false 是工具返回失败(两者都算 span 错误)

### 跟 Think 阶段对比

| 维度 | Think | Act |
|---|---|---|
| 串并行 | 单次 LLM 调用(内部流式) | 多工具并行/串行 |
| 重试 | isTransientError 2 次退避 | 无(失败让模型换思路) |
| 降级 | 优雅降级合成答案 | 无(失败返回错误给模型) |
| 超时 | 120s chunk 间 | 60s / 10m5s(shell_exec) |
| 消毒 | SanitizeMessages | 无(只动参数不动 messages) |
| 可观测性 | prompt cache 指纹 | langfuse span + PipelineInfo |
| 错误处理 | 临时错重试,大错降级 | 解析失败修复 JSON,修复失败返回错误 |

设计哲学差异:Think 是"跟模型对话"(有重试有降级,模型卡了给用户答案);Act 是"干活"(失败就告诉模型,让模型换思路,不替模型兜底)。
