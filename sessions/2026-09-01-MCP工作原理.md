## 关键发现(给 AI 自己看,防失忆)

### MCP 三角色

- **Host**:跑 LLM 的总管(WeKnora 后端),管 Agent 引擎 + ToolRegistry + MCPManager
- **Client**:Host 里的外交官,一个 Server 配一个,走 MCP 协议
- **Server**:独立干活的外部程序(GitHub/Slack/DB),暴露 ListTools/CallTool

### 三层关系

```
Host
  ├─ Agent 引擎(调 LLM)
  ├─ ToolRegistry(工具注册表)
  └─ MCPManager
       ├─ Client A (stdio) ── Server A (GitHub)
       ├─ Client B (SSE)   ── Server B (Slack)
       └─ Client C (HTTP)  ── Server C (DB)
```

### MCP 协议核心

- **JSON-RPC 2.0** 格式
- **三种传输**:stdio(本地子进程)/ SSE(HTTP 长连接)/ HTTP(请求响应)
- **握手**:Initialize → InitializeResult → Initialized → 之后反复 ListTools/CallTool

### 三类原语

| 原语 | 作用 | 副作用 | WeKnora 用 |
|---|---|---|---|
| Tools | 模型主动调 | 有(建仓库/发消息) | ✅ ListTools/CallTool |
| Resources | 模型读 | 无(读文件/查配置) | ✅ ListResources/ReadResource |
| Prompts | 提示词模板 | 无 | ❌ 没用 |

### stdio 传输的特殊性

- 每次启 agent 建子进程,用完得杀(不然僵尸进程)
- mcp_tool.go:458 `defer client.Disconnect()` 杀子进程
- 断了不重连(重连得重启子进程),SSE/HTTP 才重连

### 完整调用链(GitHub 建仓库)

```
配置阶段(管理员):
  配 MCP 服务(github/stdio/npx + GITHUB_TOKEN)→ 存 DB

启动阶段(每次启 agent):
  registerMCPTools → RegisterMCPTools
    → getOrCreateMCPClientWithOAuthRetry(stdio 连接:启动 npx 进程)
    → Client.Initialize() 握手
    → Client.ListTools() 拉 [create_repo, ...]
    → 包成 MCPTool 注册进 ToolRegistry

调用阶段(用户对话):
  用户:"帮我建个叫 demo 的仓库"
  → LLM 决定调 mcp_github_create_repo(name="demo")
  → ExecuteTool 7 步 → MCPTool.Execute
  → Approval 闸弹框(危险工具)
  → 用户点同意
  → Client.CallTool("create_repo", {name:"demo"})
  → GitHub Server 调 GitHub API: POST /user/repos
  → 返回 {repo_url: "https://github.com/user/demo"}
  → 回 Agent → 喂 LLM → 回用户
```

### USB 类比

- Host = 电脑(只认 USB 协议)
- Client = USB 控制器(管协议握手)
- Server = USB 设备(键盘/鼠标/摄像头,内部不同但都走 USB)

电脑不用知道连的是啥设备,USB 协议标准化了。MCP 一样,WeKnora 不用知道连的是 GitHub 还是 Slack,MCP 协议标准化了。

### 为啥要三层解耦

- 不三层:Host 直接调每个 Server,每接一个新服务写一套适配代码,Host 膨胀成怪物
- 三层:Server 按 MCP 协议暴露能力,Host 只调 Client.ListTools/CallTool,Client 翻译协议
- 解耦 + 标准化,新接一个 Server 不用改 Host 代码
