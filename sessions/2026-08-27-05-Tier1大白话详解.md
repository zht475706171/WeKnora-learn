## 我做了什么

1. 看 `internal/types/chunk.go` 的 Chunk struct 定义 —— 关键发现:
   - `ContextHeader string json:"-" gorm:"type:text"`
   - `json:"-"` = 不序列化到 API(前端看不到)
   - `gorm:"type:text"` = **持久化到数据库**
   - 注释明确:"It is persisted so a later content edit can rebuild the same index input"
   - 证实 ContextHeader 是单独存的,不进 Content

2. grep 找 `EmbeddingContent` 的调用点 —— 找到 `knowledge_process.go:519`:
   ```go
   indexContent := buildKnowledgeIndexContent(knowledge, chunk.EmbeddingContent())
   ```
   这里在生成索引时临时拼接 ContextHeader + Content,然后喂给 embedding 模型

3. 看 `knowledge_index_content.go::buildKnowledgeIndexContent` —— 进一步在前面拼文档标题:
   ```go
   return title + "\n" + content
   ```
   最终喂给 embedding 模型的输入 = `文档标题\n面包屑\n\n正文`

4. 完整链路理清:
   - chunks 表存 Content(纯正文) + ContextHeader(面包屑) + 位置
   - 索引时调 EmbeddingContent() 临时拼出"面包屑\n正文"
   - 再调 buildKnowledgeIndexContent 拼出"文档标题\n面包屑\n正文"
   - 喂给 embedding 模型生成向量
   - 向量进向量库(pgvector 等)
   - Content 和 ContextHeader 留在 chunks 表供业务用

5. 重读 heading_splitter.go 的 sectionBreadcrumbs 和 breadcrumbAtOffset,确认问题 4 的机制:
   - sectionBreadcrumbs 扫 section 内子标题,记录(rune偏移, 当时栈快照)列表
   - breadcrumbAtOffset 用子 chunk 的 Start 位置二分查找最后一个不超过的栈快照
   - 实现超大 section 二次切后子 chunk 仍带正确子标题面包屑

## 关键发现(给 AI 自己看,防失忆)

- ContextHeader 有 gorm tag → 持久化到数据库,有 json:"-" → 不给前端
- 注释明确持久化目的:让 content 编辑后能重建一样的索引输入
- EmbeddingContent() 是临时拼接函数,不持久化结果
- 索引链路:chunk.EmbeddingContent() → buildKnowledgeIndexContent(再拼文档标题) → 喂 embedding 模型 → 向量入库
- "最低层级"=层级数字最小=最靠根=H1 < H2 < H3,不是 H3
- MdHeadingCounts[level]++ 在 ProfileDocument 扫每行时,通过 matchHeading 用 MarkdownHeadingPattern 匹配
- ≥3 次防止"文档只有一个 H1 切成开头+全文"
- sectionBreadcrumbs 返回 [(runeStart, breadcrumb), ...],breadcrumbAtOffset 用 chunk.Start 找最后不超过的栈快照
- 完整例子见 notes/05
