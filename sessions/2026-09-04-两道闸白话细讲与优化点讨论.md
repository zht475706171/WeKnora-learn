## 关键发现(给 AI 自己看,防失忆)

### 闸 1 白话要点

- 触发:估算 > 窗口 - 16K(Reserve 给回答留空间)
- 圈地:从队尾往回攒 ≤ 2 万(KeepRecent),预算是天花板不是地板(单条检索结果可上万)
- 切点铁律:tool 结果不可下刀(OpenAI 配对),system 禁区
- split turn:轮次太肥被劈两半 → 前半段单独摘要"前情提要"(Original Request / Early Progress / Context for Suffix)
- 摘要模板 8 栏:Goal / Constraints / Progress(Done/In Progress/Blocked)/ Key Decisions / Next Steps / Critical Context;强调路径数字报错原文原样保留;500 词内
- initial vs update:update 规则"CONDENSE as you go,不许比旧摘要长"(防摘要自己膨胀吃掉腾出的空间)
- 保险丝:Temperature 0.3 / 2 次重试 60s 超时 / validateSummary 拒绝空+length 截断(残缺摘要每轮继承)/ 全挂 rawArchive 降级 degraded=true / CacheRetention None
- 防注入:对话包 <conversation>,指令放最后
- 装配:[system, SummaryMessage(user 消息+Kind 标记), 尾部];user 而非 system(保 cache+语义对);Kind 供下轮识别做增量更新
- 验收:释放 ≥ 5%(minFreedFraction);不过标记 compactionExhaustedAt(记条数不记布尔,消息涨了结论过期可重试)

### 闸 2 白话要点

- 定位:搬家车装不下现场扔东西(纯规则,免费,真丢)
- 三条出场路径:Compaction 后还超 / 没东西可压 / overflow 强压失败
- 盲区:单条巨型工具结果在保留区,切点够不着
- 预算:所有 tool 消息合计 ≤ 窗口/5(下限 8K 上限 32K)
- 两步走:先全没收发收据(original_bytes+咋办提示),再从最新往最旧用剩余预算赎回(最新的最可能马上用到)
- 预览:头 1/4 尾 3/4(尾部多因结论性内容在末尾),二分查找最大可塞长度
- 三铁律:只动 tool Content 不动 ToolCalls(配对)/ 返回拷贝不改原件(SSE 诊断持久化还在用)/ 全部 tool 结果都是候选(Compaction 后保留区全是 recent,无新旧可挑)

### 跟 Claude Code autocompact 对比

- 同族方案(LLM-generated memory),模板趋同(都是结构化交接表,8 段左右)
- 真差异:外部记忆有无(文件系统可重读 vs 无外部记忆必须留原文)/ 压缩位置(turn 边界 vs ReAct loop 内每轮)/ split turn 需求 / 5% 验收和 degraded 降级是 WeKnora 特有工程防护
- Claude Code compact 摘要持久化(session 文件),WeKnora 不持久化——正是优化点 1 要补的

### 两闸搭配 5 个不足

1. 跨 turn 重复摘要(SummaryMessage 内存态,turn 结束丢,同批历史每 turn 重摘)← 最大浪费
2. 同步阻塞(触发轮双倍延迟,最坏 2 分钟)
3. 摘要质量单点快照(错了滚雪球放大,无校对无回滚)
4. 触发靠事后灭火(BPE 估算有漂移,overflow 恢复兜底)
5. 三不管缝隙(保留区巨型 user/assistant 消息,闸 2 铁律只动 tool)

### 用户优化点(已结构化落盘笔记 38)

- 原始方案:工具 X 次或 token 阈值(20 万)或笔记上新增 10 万 → 触发异步摘要(不摘要 system)→ 记录 id 范围入库 → 机制 1 触发时先查笔记,存在直接替换不跑 LLM
- 理性评估:方向 9/10 描述 5/10
- 三硬伤:触发时机写死绝对值(应 阈值×0.8 相对值)/ 直接用笔记有静默丢历史雷(水位线必须对齐,否则笔记+增量)/ 不摘要 system 是现状非特性
- 隐性收益:LoadAgentHistory 从水位线开始重建,省 LLM 钱+DB IO+可能不触发 Compaction
- 分三步落地:①摘要持久化最小版(80% 收益 20% 工程量,同步无竞态)→ ②水位线机制(为异步铺路)→ ③异步预触发(阈值×0.8,快照+版本号)
- 判断:值得做不急;跳步风险高

## 后续追加讨论(同日)

### 追加 1:压缩理解校验(入库意义)

用户问:"DB 内容是全的,只是工具结果简化了,每次进来加载很多历史再触发压缩,对吧?压缩内容没入库,因为每次压缩条数不一样,所以入库意义不大,对吗?多轮对话可能压缩到同一条消息"

校验结果(对两半,关键推论反了):
- ✅ DB 全量真相,但**简化发生在读取**(CompactToolOutputForHistory 在 LoadAgentHistory 路径),不在入库;DB 原件不动
- ❌ "范围不一样 → 入库意义不大"反了:范围不一样不是入库无意义的理由,是**必须带水位线**的理由;下次范围变了走增量(旧笔记覆盖 1~50 + 现场摘 51~60),只为差额付费,不是重摘全量
- ✅ 同段历史反复被摘(turn 5 摘 [1~4] → turn 6 摘 [1~5] → turn 8 摘 [1~7],头部几轮被摘五六遍)——持久化直接干掉这个重复付费

关键心智:摘要不是裸文本,是**带覆盖范围的存档** {summary, 覆盖 1~50}。"范围不一样"杀死的是"裸文本入库"这个偷懒做法,带水位线后范围差异反而是增量复用的支点。

### 追加 2:压缩粒度阶梯(笔记 39)

用户自己抽象出"从细到粗"框架:细(单工具结果简要)→ 中(单轮总工具结果压缩:先占位符再从后往前填充)→ 粗(超阈值触发摘要)。

校验结果:框架对,漏一层,修一处:
- **漏的**:细+ 层 `redactHistoryKBResults`(跨 turn KB 结果强制涂黑)——动机不是省 token 是**防陈旧**(KB 可能被改),不分大小强制涂黑,容易被忽略
- **修的**:闸 2 作用域不是"单轮",是**保留区内所有 tool 消息**(Compaction 后保留区全 recent,无新老可挑;代码注释明确从"当前 turn"改成了"全部候选")
- **补的**:闸 2 三条出场路径(Compaction 后还超 / 没东西可压 / overflow 强压失败),不是固定在 Compaction 之后

最终四级阶梯:
1. ①细 CompactToolOutputForHistory(读 DB 时,按类型裁元信息)
2. ②细+ redactHistoryKBResults(装配时,防陈旧强制涂黑)
3. ③粗 闸 1 Compaction(loop 内,超阈值摘要替换)
4. ④中 闸 2 trimToolResults(兜底,tool 合计超窗口/5)

设计观察:
- 便宜的先上贵的最后上(①②④零成本每次做;③花钱,阈值+验收+降级三重保险)
- 作用域嵌套不重叠,各自盲区被下一级补上
- 每级都有"可恢复"出口(①④可重跑工具,②逼重新检索,③保 Critical Context)
- 唯一没持久化的是 ③(花钱买的一次性消费)——正是优化点 1 动机
