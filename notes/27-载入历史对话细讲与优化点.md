# 27 · 载入历史对话细讲(KnowledgeQA 路径)与优化点

> 用户细问:载入历史对话怎么载入的?用了哪些机制?有没有可优化地方?
> 本篇细讲 KnowledgeQA 路径(chat_pipeline)的历史载入。Agent 路径另有一套(agent_history.go),本篇不讲。

---

## 一句话

> **KnowledgeQA 路径载入历史是 pipeline 第1阶段 LOAD_HISTORY,在 query 改写之前(改写要用历史做指代消解)。5 步载入:DB取最近20行→按request_id配对成轮→丢弃RenderedContent(检索结果原文不进历史,省token大头)+剥think标签+补图片caption/附件→丢不完整轮→倒序截到最近5轮→反转正序。核心决策是"丢弃历史检索结果原文",代价是 KnowledgeQA 路径没有运行时压缩(不像Agent路径有LLM摘要+硬截断两道闸),长会话靠maxRounds硬上限兜,这是最该优化的点。**

---

## 一、载入历史:5 步细讲

### 1.1 触发时机:pipeline 第 1 阶段,在 query 改写之前

`PluginLoadHistory`(load_history.go:11)监听 LOAD_HISTORY 事件,是检索 pipeline 第1阶段,**在 QUERY_UNDERSTAND(改写query)之前跑**。因为改写 query 要用历史做指代消解("它和传统搜索有什么区别"→"RAG和传统搜索..."),历史必须先载入改写才能拿到上下文。

### 1.2 Step 0:判断要不要载入

```go
// load_history.go:40
if chatManage.MaxRounds <= 0 {
    return next()   // multi_turn_disabled,跳过不载入
}
maxRounds := chatManage.MaxRounds   // 默认 5
```
MaxRounds<=0=多轮被显式禁用(custom agent设MultiTurnEnabled=false),直接跳过历史不泄漏进LLM。注释强调**不回退全局默认值**,否则禁用开关被静默覆盖——尊重用户配置的设计。

### 1.3 Step 1:DB 取最近 N 条原始消息行

```go
// common.go:152
history, err := messageService.GetRecentMessagesBySession(ctx, sessionID, fetchCount)
// fetchCount = maxRounds*2+10 = 5*2+10 = 20
```
DB 查询 `ORDER BY created_at DESC LIMIT 20`——**取最近20条原始message行**。取的是行不是轮(每轮=user行+assistant行=2行)。maxRounds*2+10留10条余量,防末尾几轮配对不全凑不够5轮。

### 1.4 Step 2:按 request_id 配对成轮(核心)

```go
// common.go:157-182
historyMap := make(map[string]*types.History)
for _, message := range history {
    h, ok := historyMap[message.RequestID]
    if !ok { h = &types.History{} }
    if message.Role == "user" {
        h.Query = message.Content              // ★ 只取原始Content
        // ★★ 丢弃RenderedContent(检索结果原文)!
        if desc := extractImageCaptions(...); desc != "" {
            h.Query += "\n\n[用户上传图片内容]\n" + desc   // 图片caption补进query
        }
        if len(message.Attachments) > 0 {
            h.Query += message.Attachments.BuildPrompt()   // 附件补进query
        }
    } else {
        h.Answer = regThinkTags.ReplaceAllString(message.Content, "")  // ★ 剥think标签
        h.KnowledgeReferences = message.KnowledgeReferences
    }
    historyMap[message.RequestID] = h
}
```

三个关键动作:
- **①丢弃RenderedContent**(common.go:163注释):上一轮检索结果(可能几KB)在历史里不保留原文,只留用户原始问题。**省token大头**。注释:重放RenderedContent会把旧`<context id="...">`信封和旧引用指令混进当前协议;历史引用单独放KnowledgeReferences可在当前轮重新合并。
- **②剥`<think>`标签**(common.go:178):推理模型`<think>...</think>`内部推理块去掉。think块给历史用是噪声,剥掉省token+防干扰。
- **③图片caption/附件补进query**(common.go:171-176):历史里上一轮用户传图,caption以`[用户上传图片内容]`补进query;附件也补。多轮时模型还能"记得"上一轮传过什么。

### 1.5 Step 3:丢不完整轮

```go
// common.go:184-189
for _, h := range historyMap {
    if h.Answer != "" && h.Query != "" {   // 必须问和答都有
        historyList = append(historyList, h)
    }
}
```
只有query和answer都非空的轮才保留。某轮只有user问assistant没答完(或答失败),丢掉——不完整上下文反而干扰。

### 1.6 Step 4:倒序排+截到maxRounds

```go
// common.go:191-197
sort.Slice(historyList, func(i, j int) bool {
    return historyList[i].CreateAt.After(historyList[j].CreateAt)  // 倒序最新在前
})
if len(historyList) > maxRounds {
    historyList = historyList[:maxRounds]   // 截最近5轮
}
```

### 1.7 Step 5:反转成正序

```go
// common.go:199
slices.Reverse(historyList)   // 转回正序(最旧在前最新在后)
```
截完反转成正序(LLM按时间顺序读)。写入 chatManage.History。

### 1.8 怎么用:组装进 LLM prompt

`prepareMessagesWithHistory`(common.go:87):
```go
chatMessages := []chat.Message{
    {Role: "system", Content: systemPrompt},                          // system(含检索context+记忆)
}
chatMessages = AppendHistoryMessages(chatMessages, chatManage.History)  // 历史轮次
chatMessages = append(chatMessages, userMsg)                          // 当前轮
```
AppendHistoryMessages(common.go:134)每轮展开user+assistant两条。

最终发给LLM:
```
system:    [system prompt + 检索context + 记忆]
user:      历史第1轮query
assistant: 历史第1轮answer
...
user:      当前轮query(含本轮检索context)
```

## 二、用了哪些机制(汇总)

| 机制 | 位置 | 作用 |
|------|------|------|
| MaxRounds截断 | common.go:195 | 取最近5轮,不全部载入 |
| 多fetch余量 | common.go:152 | 取20行(5×2+10),防配对不全凑不够5轮 |
| request_id配对 | common.go:157 | user行+assistant行配成轮 |
| **丢弃RenderedContent** | common.go:163 | 历史检索结果原文不进context(省token大头) |
| 剥think标签 | common.go:178 | 去推理过程噪声 |
| 图片caption/附件补进query | common.go:171-176 | 多轮记得上传过什么 |
| 丢不完整轮 | common.go:186 | query/答缺一的轮丢弃 |
| 时间正序 | common.go:199 | LLM按顺序读 |
| 历史引用单独携带 | common.go:179 | KnowledgeReferences不进历史文本,merge阶段相似度过滤后重注入(最多3条6折) |
| 多轮禁用开关 | load_history.go:40 | MaxRounds<=0跳过,不回退默认 |

## 三、可优化的地方(4个,按价值排)

### 优化点1(中价值):固定maxRounds截断,不按token自适应

**现状**:硬截最近5轮(common.go:195),不管这5轮多长。长回答5轮十几K token,短回答5轮才几百token。
**问题**:固定条数不固定token,跟实际context占用脱节。
**优化**:按token预算倒序填充——从最新轮往回加,加到接近token预算停。长回答自动少载、短回答自动多载。
**代价**:需token估算(Agent路径已有tokenEstimator,KnowledgeQA没有要引入)。注意这是Agent路径已有能力,KnowledgeQA没复用,不对称。

### 优化点2(高价值,最该做):KnowledgeQA路径没有运行时压缩,长会话必崩

**现状**:KnowledgeQA路径**只有载入时截断,没有运行时压缩**。Agent路径有Consolidator(LLM摘要50%)+CompressContext(硬截80%)两道闸,**KnowledgeQA一道都没有**。
**问题**:maxRounds=5是硬上限,但用户配max_rounds=20/50(长会话),KnowledgeQA没任何兜底——20轮全塞context必爆。完全依赖"用户别配太大"脆弱假设。
**优化**:把Agent路径manageContextWindow(observe.go:26)那套闸下放到KnowledgeQA——超阈值LLM摘要旧历史+硬截断。代码现成是复用不是新写。
**代价**:低(代码已有接进来即可)。**最该做的优化——两路径能力不对称,KnowledgeQA缺安全网。**

### 优化点3(低价值,锦上添花):历史只取原始Query,丢了上一轮"检索了什么"

**现状**:载入时丢弃RenderedContent,历史只有用户原始问题,没"上一轮检索到哪些chunk"。是权衡不是bug——丢弃为省token+防旧context格式混入。代价:多轮追问时模型不知上一轮基于哪些文档答的,只能靠KnowledgeReferences在merge阶段相似度过滤后重注入(最多3条6折)。
**问题**:Jaccard>0.15相似度过滤可能滤掉上一轮真正相关引用(当前query措辞跟上一轮引用chunk文本不重叠时)。模型丢失"上一轮证据"。
**优化**:不全丢,把上一轮KnowledgeReferences压缩成简短引用标记(如`[上轮引用: doc1,doc2]`)补进历史answer,而非要么全留要么全丢。模型知上一轮引用什么又不占大量token。
**代价**:中(设计压缩格式+不破坏当前协议)。

### 优化点4(低价值):fetch余量+配对逻辑可能少载

**现状**:fetchCount=20行。末尾几轮assistant回答慢/失败(只有user行),配对时被丢(Step3),20行可能凑不够5轮完整对。
**问题**:极端情况(多轮失败率高)实际载入<5轮。
**优化**:fetchCount余量加大或失败后回查更多。边缘场景价值低。

### 优化总结(工程判断)

| 优化点 | 价值 | 改动 | 推荐? |
|--------|------|------|-------|
| ① 按token预算自适应 | 中 | 中(引入token估算) | 可做 |
| ② **KnowledgeQA复用Agent压缩闸** | **高** | **低(代码现成)** | **最该做** |
| ③ 历史保留压缩引用标记 | 中 | 中 | 锦上添花 |
| ④ fetch余量加大 | 低 | 低 | 边缘 |

核心判断:最该改优化点2——KnowledgeQA路径没运行时压缩,跟Agent路径能力不对称。Agent有两道闸兜长会话,KnowledgeQA一道都没有靠maxRounds硬上限。把Agent的manageContextWindow接过来是现成代码复用,代价低收益高,补长会话安全网。
