## 优化点 1:异步预压缩 + 笔记持久化 + 命中复用

### 动机

当前机制(笔记 37 讲的链路)有两个痛点:

1. **跨 turn 重复摘要(最大浪费)**:`SummaryMessage` 只活在单次 Execute 的内存里,turn 结束写 DB 时没地方存摘要。下一轮 LoadAgentHistory 从 DB 重建完整历史(只有规则压缩/涂黑),进 loop 又超阈值,又触发 Compaction,又花一次 LLM 钱把同一批历史再摘一遍。长会话聊 10 轮,历史中段可能被摘七八遍。

2. **同步阻塞**:Compaction 串在主 LLM 调用前,触发那一轮用户要等"摘要调用 + 主调用"两段延迟。最坏 60s × 2 次重试,光摘要就 2 分钟。

### 方案(用户原始描述,结构化)

**触发时机**(三选一,满足任一即触发异步摘要):
- 工具执行累计达到 X 次
- 估算 token 达到阈值(例如 20 万)
- 在已有笔记基础上再新增 10 万 token

**异步执行**:
- fork 一个独立 goroutine(不需要真子 agent,`summarize` 本来就是独立 chat 调用)
- 拿 fork 时刻的 messages 快照
- 对快照做摘要(**不摘要 system prompt**)
- 记录"本次摘要覆盖的消息 id 范围 [起点, 终点]"
- 摘要 + id 范围 + 水位线 + created_at 入库

**主 loop 触发 Compaction 时**:
- 先查库里有没有笔记
- 笔记存在且水位线对齐 → **直接用笔记替换 [起点, 终点] 的内容,不跑 LLM 摘要**
- 笔记存在但水位线不够 → 笔记 + 小段增量摘要(覆盖笔记终点到当前切点)
- 笔记不存在 → 现场摘要(现状,兜底)

**收益**:省去同步调用的成本;跨 turn 复用,同一批历史只摘一次。

### 落地要点

1. **水位线对齐是命门**
   - 笔记不能只存"摘要内容",必须存"我覆盖到哪":消息 id 范围、消息 hash、turn 边界,任选一种或多种
   - 因为 fork 之后主 loop 还在跑,消息还在涨,真正触发时切点可能在笔记终点之后
   - "直接用笔记"必须修正为"笔记 + 增量摘要",否则会静默丢一段历史
   - 只有水位线恰好对齐时才能完全免跑

2. **预触发时机不能太早**
   - "到 20 万 token 或 X 次工具调用"这个时机偏早,离阈值(窗口 - 16K)还远
   - 大部分对话根本到不了阈值,提前跑的摘要就是白烧的钱
   - 合理预触发点:`估算 > 阈值 × 0.8` 时 fork
   - 太早浪费,太晚笔记还没写完主 loop 就先触发了,等于没优化

3. **竞态用快照 + 版本号模式,不用锁**
   - 子 goroutine 只读 fork 时刻的快照,不碰主 loop 可变状态
   - 笔记写独立存储(DB 新表或 messages 表新 kind)
   - 主 loop 用笔记时按水位线校验
   - 不需要复杂锁

4. **笔记持久化形态**
   - DB 新表:`session_compaction_notes(session_id, summary, start_msg_id, end_msg_id, token_at, created_at)`
   - 或 messages 表新 Kind:`MessageKindAsyncCompactionNote`(跟现有 `MessageKindCompactionSummary` 区分)
   - LoadAgentHistory 读历史时:读到笔记 → 直接拼 SummaryMessage 进历史,历史从"笔记水位线"开始重建,不用重新摘要整段

5. **摘要内容跟现有 Compaction 共用模板**
   - 复用 `prompts.go` 的 8 章节模板
   - 复用 `initialSummarizationInstructions` / `updateSummarizationInstructions`(有旧笔记就用 update,越更新越短)
   - 复用 `validateSummary`(拒绝空响应 + length 截断)
   - 复用 `CacheRetention: None`(摘要禁缓存)

### 坑(必须想清楚的)

- **笔记失效**:KB 被改/切/删,笔记里的 Critical Context(chunk_id、检索结果)过期了怎么办?
  - 现有 `redactHistoryKBResults` 是在装配时涂黑,笔记如果在涂黑之前摘的,里面已经有 KB 内容
  - 方案:笔记入库时记录涉及的 KB id,KB 变更时标记笔记失效;或者笔记内容里不带 KB 具体内容,只带"用户问过 X,用 KB Y 检索过 Z"
- **多轮笔记叠加**:笔记之上再 fork 笔记,水位线怎么管?
  - 笔记 A 覆盖 1~50,笔记 B 覆盖 51~80,触发时切点在 90
  - 是用最新的笔记 B + 增量摘要 80~90?还是把笔记 A + B 合并?
  - 倾向:用最新笔记 + 增量,旧笔记在 update 指令下自然滚进新笔记
- **fork 时主 loop 还在跑**:fork 时刻的"终点"在 fork 之后可能被新消息覆盖
  - 终点用消息 id 而不是位置索引,消息 id 不可变
  - 摘要进行中主 loop 追加的新消息不在笔记覆盖范围,自然落到增量摘要里

### 对照业界

- **Claude Code 的 compact 摘要就是持久化的**:存在 session 文件里,恢复会话摘要还在,不重摘。正好是它比 WeKnora 当前实现做得好的地方。
- **预取/预测式压缩**(prefetch):数据库和浏览器缓存的标准玩法,趁空闲把马上要用的重活先干掉。

### 收益排序

1. **持久化复用**(跨 turn 不重摘)——最大收益,每个长会话持续省钱
2. **消除同步阻塞**(异步预跑)——偶尔卡一下变完全不卡
3. **提前量**(预触发)——边际收益,前提是时机不能太早

### 风险排序

1. 水位线对齐做错 → 静默丢历史(最严重)
2. 预触发时机太早 → 白烧 LLM 钱
3. 笔记失效检测漏掉 → 用过期信息回答(跟现有 redact 同源问题,可复用方案)

### 理性评估(讨论后共识)

**评分:方向 9/10,当前描述 5/10。** 方向是真优化(痛点真实、跟业界验证过的做法同向),但当前描述有三个硬伤:

1. **触发时机拍脑袋**:"20 万 token / X 次工具"写死绝对值。模型窗口大小不一(32K/128K/200K),大部分对话到不了阈值,提前跑的摘要就是白烧。应改成相对值:`估算 > 阈值 × 0.8` 时触发。
2. **"直接用笔记"藏着静默丢历史的雷**:fork 之后主 loop 还在跑,真触发时切点可能在笔记终点之后。举例:笔记覆盖 1~50,主 loop 涨到 60 条,切点在 55 → "直接用笔记" = 51~55 这段历史丢了(没人摘要它,原文也过了切点)。必须修正成"笔记 + 增量摘要",只有水位线恰好对齐才完全免跑。
3. **"不摘要 system"是现状不是特性**:现有 `historyStart` 本来就跳过 system。

**隐性收益(方案描述里没写但真实存在)**:笔记入库后,LoadAgentHistory 从"笔记水位线"开始重建历史,不用把整段历史拉出来再摘要。省摘要 LLM 钱 + DB IO + token 估算开销,历史段进 loop 前可能就已经低于阈值,根本触发不了 Compaction。

**成本**:DB schema 改动(中)+ LoadAgentHistory 改造(中)+ 水位线机制(中,容易做错)+ 笔记失效(小,可复用 redact 逻辑)+ 竞态处理(小,快照+版本号)+ 测试覆盖(中,异步跨 turn 场景多)。

**判断:值得做,但不急。** 痛点真实但非致命(是优化空间不是 bug);改动面不小;水位线做错静默丢历史比重复摘要更可怕。

### 分步落地方案(推荐路径)

不跳步,分三步,每步独立可验证:

**第 1 步:摘要持久化最小版(拿 80% 收益,工程量 20%)**
- 同步、不预触发、不异步
- turn 结束把 SummaryMessage 写 DB(messages 表新 Kind 或新表)
- 下轮 LoadAgentHistory 读出来,直接拼进历史
- 效果:同一批历史只摘一次,跨 turn 复用
- 风险:低(纯持久化,无竞态无水位线)

**第 2 步:加水位线机制(为异步做准备)**
- 笔记记录覆盖范围(消息 id 范围)
- 装配时按水位线对齐:对齐 → 直接用;不对齐 → 笔记 + 增量摘要
- 这步做完,异步才有安全基础

**第 3 步:异步预触发(最后加)**
- 水位线机制稳定后,把摘要挪到 goroutine
- 预触发点:`估算 > 阈值 × 0.8`(相对值,不写死)
- 快照 + 版本号模式,不加锁

**跳过第 1 步直接做 2+3 = 风险高;分三步走 = 每步独立验证,稳。**
