# 03 · Go 后端的切块是怎么切的(大白话版)

> 学习目标:看懂 docreader 吐回来的 Markdown,是怎么被 Go 后端切成一个一个 chunk,准备喂给 Embedding 模型的。
>
> 关键结论先放前面:**docreader 自己也有一份 Python 切块代码(`splitter/splitter.py`),但生产路径已经迁到 Go 侧的 `internal/infrastructure/chunker/`**。Python 那份是 sidecar 残留,WeKnora 现在用 Go 切。

---

## 一句话总结

WeKnora 的切块不是"无脑按字数切",而是**先给文档做"体检",根据它的结构(有没有 Markdown 标题?有没有"第一章"这种章节标记?)选合适的切法,切完还要校验,切得不好就降级到下一档**。三层切法 + 自动降级,这就是 WeKnora 切块的核心设计。

---

## 切块在整个流程里的位置

```
[docreader 返回 Markdown]
    │
    ▼
[Go 后端 internal/application/service/knowledge_process.go]
    │
    ├─ Step 1: 图片处理(本地/远程图片解析存到对象存储)
    │
    ├─ Step 2: 规范化换行(CRLF→LF,避免同样内容切出不同 chunk)
    │
    ├─ Step 3: ★ 切块 ★   ← 本篇讲这里
    │   buildSplitterConfig()  拿配置
    │   如果启用父子分块:chunker.SplitParentChild()
    │   否则:chunker.Split()
    │
    ├─ Step 4: 把切出来的 chunk 转成 ParsedChunk
    │
    ▼
[向量化 → 入库]
```

调用入口就两个函数:
- `chunker.Split(text, cfg)` —— 单层切
- `chunker.SplitParentChild(text, parentCfg, childCfg)` —— 父子双层切(更多用)

## 三层切法(Strategy Tier)

WeKnora 把切法做成"分层链路",一层不行下一层:

| Tier | 名字 | 适合什么文档 | 干啥 |
|------|------|------------|------|
| Tier 1 | **heading**(标题切) | 有清晰 Markdown 标题(# ## ###)的文档 | 按标题分块,每个 chunk 自带标题面包屑 |
| Tier 2 | **heuristic**(启发式) | 没标题但有"第一章"/"1.1"/"Kapitel"等结构标记的文档 | 用正则找章节边界 |
| Tier 3 | **legacy**(递归切) | 啥结构都没有的纯流水文本 | 按分隔符递归切 + 重叠 |

**关键:三层是 fallback 链,不是三选一**。先试 Tier 1,切完校验不过 → 试 Tier 2 → 再不过 → Tier 3(永远会出结果)。

---

## 入口 `strategy.go` 干啥

```go
func Split(text, cfg) []Chunk {
    chain, profile := resolveChainWithProfile(text, cfg)  // 选链
    for _, tier := range chain {
        out := runTier(tier, text, cfg, profile)            // 跑这层
        if ValidateChunks(out, ...) OK {                    // 校验
            return out
        }
        // 不行就下一层
    }
    return SplitText(text, cfg)  // 最终兜底
}
```

链怎么选?看 `cfg.Strategy`:
- `"heading"` → 直接 `[TierHeading, TierLegacy]`
- `"heuristic"` → `[TierHeuristic, TierLegacy]`
- `"legacy"` 或空 → `[TierLegacy]`(兼容老配置)
- `"auto"`(默认)→ **给文档做体检,自动选**

## 文档体检 `profiler.go`(auto 模式的核心)

`ProfileDocument(text)` 扫一遍文档,统计这些信号:

```
DocProfile {
  TotalChars, TotalLines, AvgLineLen, StdLineLen  // 基础统计

  // Markdown 结构
  MdHeadingCounts  // 每级标题(# 到 ######)各有多少个
  MdHeadingTotal   // 标题总数

  // 启发式结构标记
  NumberedSectionCount      // "1.1", "1.2.3" 这种编号
  GermanChapterCount        // "Kapitel 1"(德语)
  EnglishChapterCount       // "Chapter 1"
  ChineseChapterCount       // "第一章"
  AllCapsShortLineCount    // 短的全大写行(像 "INTRODUCTION")
  VisualSepCount            // "---" 之类的视觉分隔符
  FormFeedCount            // \f 分页符

  HasTables, HasCode, CodeRatio  // 表格/代码

  DetectedLangs  // 检测到的语言
}
```

然后 `SelectStrategy(profile)` 按规则选链:

```
if Markdown标题 ≥ 3 个 且 标题密度 > 0.5% 且 有主导标题层级:
    chain.append(TierHeading)   // Tier 1 候选

if 启发式标记 ≥ 5 个 或 有 \f 或 有章节标记(中/英/德):
    chain.append(TierHeuristic)  // Tier 2 候选

chain.append(TierLegacy)         // 永远兜底
```

> 翻译成人话:**先看文档有没有 Markdown 标题结构,有就用标题切;再看有没有"第一章"之类的章节信号,有就用启发式切;最后不管怎样都把递归切当兜底。**

## Tier 3 兜底:`splitter.go::SplitText`(递归切)

这是最基础也是最稳的切法,任何文档都能切出结果。流程:

```
Step 1: protectedSpans(text)
   找出"不能被切开"的内容(正则匹配):
   - LaTeX 数学 $$...$$
   - Markdown 图片 ![..](..)
   - Markdown 链接 [..](..)
   - Markdown 表格(整张表当原子单元)
   - 代码块 ```...```
   - 行内代码 `..`
   这些区域会被标记成"保护区间",切刀不会落进去。

Step 2: buildUnitsWithProtection(text, protected, separators, chunkSize)
   把文本切成"原子单元":
   - 普通文本:按分隔符 [\n\n, \n, 。] 递归切
     (先用 \n\n 切,如果切完还有单元 > chunkSize,
      就对那个大单元再用 \n 切,以此类推)
   - 保护区间:整块当一个原子单元,不切
   - 如果某个保护单元超过 7500 字(比如一个巨型表格),
     强制按行/空格切(留 200 字搜索边界)

Step 3: mergeUnits(units, chunkSize, chunkOverlap)
   把原子单元合并成 chunk,带 overlap:
   - 一个个往当前 chunk 里塞,塞不下就封口开新 chunk
   - 新 chunk 会从前一个 chunk 末尾借一段当 overlap
     (overlap 不是硬切字符,而是找语义边界:
      段落断\n\n > 行断\n > 句号。?!)
   - 表格边界强制封口(避免下个表继承上个表的表头)
   - 标题面包屑会前缀到新 chunk(让 chunk 自带"我属于哪一节"上下文)

Step 4: 返回 []Chunk{Content, ContextHeader, Seq, Start, End}
   Start/End 是 rune 偏移,保证能把原文重新拼回来
```

### 默认参数

```go
DefaultChunkSize    = 512   // 字符(~100-130英文token / ~300中文token)
DefaultChunkOverlap = 80   // ~15% 重叠
Separators          = ["\n\n", "\n", "。"]
```

注释里写得很细:**512 字符是 Vecta 2026年2月基准测试 50 篇学术论文验证出来的最优值**。FAQ 类用 200-400,长叙事用 1000-2000。

### overlap 的聪明设计

`computeOverlap()` 不是傻切前 80 个字符,而是在前 chunk 末尾窗口里找"语义边界":
1. 段落断 `\n\n`(最高优先级)
2. 行断 `\n`
3. 句号 `。` / `. ` / `? ` / `! `

找不到合适的边界就**不要 overlap**,保证 deterministic 且 bounded。

## 父子双层切(`SplitTextParentChild`)—— 生产更常用

为什么要父子?RAG 里有个经典难题:
- chunk 太小 → 上下文不够,检索准但回答片面
- chunk 太大 → 检索稀,但召回率低

**父子切**解决这个:切两层
```
大窗口 parent(默认 4096 字符)→ 给 LLM 看完整上下文
  └── 切成小窗口 child(默认 384 字符)→ 拿去做向量检索
```

检索时:用 child 向量匹配(精准),返回时给 LLM 整个 parent(上下文全)。两全其美。

```go
parentCfg = {ChunkSize: 4096, ...}
childCfg  = {ChunkSize: 384, ChunkOverlap: 384/5, ...}

parents := Split(text, parentCfg)           // 先切大块
for parent in parents:
    children := Split(parent.Content, childCfg)  // 每块再切小块
    每个 child 记住 ParentIndex
```

每个 child 还会继承 parent 的 `ContextHeader`(标题面包屑),让 embedding 的时候带上"我属于哪一节"的语义。

## Chunk 结构体(切出来的最终产物)

```go
type Chunk struct {
    Content       string  // 切出来的文本(原文 rune 切片)
    ContextHeader string  // 标题面包屑(如 "# 引言\n## 背景"),embedding 时前缀加上
    Seq           int     // 第几个 chunk(全局唯一)
    Start         int     // 在原文里的 rune 起始位置
    End           int     // 在原文里的 rune 结束位置
}
```

关键不变量:`End - Start == utf8.RuneCountInString(Content)`。也就是说 **Content 必须是原文的精确切片**,不能多不能少。这点对"文档高亮"、"按位置重建文档"这些功能至关重要。

`EmbeddingContent()` 方法特别有意思:
```go
func (c Chunk) EmbeddingContent() string {
    body := strings.TrimSpace(c.Content)
    if c.ContextHeader == "" {
        return body
    }
    return c.ContextHeader + "\n\n" + body
}
```
embedding 时把标题前缀加上(让向量带着"我在哪一节"的语义),但 `Content` 本身保持纯净(位置不变量不被破坏)。

## 切完怎么校验 `validator.go`

`ValidateChunks(chunks, totalChars, chunkSize)` 检查:
- chunk 数量合理
- 起始位置递增
- 总字符数对得上(允许 overlap 导致的轻微超出)
- 没有 0 长度 chunk

不通过 → 降级到下一 tier。

## 设计上几个聪明点(值得记)

1. **三层 + 自动降级**:从最结构化(标题切)到最暴力(递归切),永远有结果。auto 模式让用户不用懂也能拿到好结果。

2. **文档体检驱动选型**:不是看用户配置,而是看文档本身长啥样。同一篇文档用 `auto` 总能选到最合适的切法。

3. **保护区间防误切**:LaTeX 公式、Markdown 表格、代码块不会被切刀劈开。一个 5000 字的表格会整块当 chunk(超 7500 才强制切)。

4. **语义 overlap**:overlap 不是字符硬切,而是找"段落/行/句号"边界,既保证连续性又不破坏语义单元。

5. **父子双层**:小 chunk 检索精准,大 chunk 上下文完整。这是现代 RAG 的主流打法。

6. **rune 偏移保证可重建**:`Start/End` 用 rune 偏移,`Content` 是原文精确切片。这让"分块编辑"、"文档高亮"、"按位置 diff"成为可能。

7. **ContextHeader 与 Content 分离**:embedding 看到带标题的版本,但 Content 保持纯净。位置不变量和语义上下文两不误。

8. **CRLF 规范化**:浏览器粘贴是 LF,文件上传保留 CRLF,不规范化会让"同样的内容切出不同的 chunk"。`NormalizeLineEndings` 在切之前统一。
