# 笔记 37 · 压缩流程完整链路(从 DB 读取到 loop 结尾)

> 接笔记 36(上下文管理最新机制变化)。上一篇按"commit 改动"视角讲,本篇按"数据流向"视角
> 从 DB 读数据 → 拼装 → 进 loop → 每轮压缩 → loop 结尾,把当前最新代码的完整流程走一遍。
>
> 风格延续:专业术语 + 白话解释双轨。

---

## 一句话总结

**压缩发生在两个时间点 + 用两种手段**。
两个时间点:**对话开始前**(DB 读取 + 拼装)和**每轮开头**(loop 内)。
两种手段:**压缩**(按规则裁,丢内容保元信息)和**摘要**(调 LLM 生成结构化摘要,保语义丢细节)。
旧版把这两件事拆成 4 道闸,新版合并成"开始前压一次 + 每轮摘要一次 + 兜底裁一次"。

---

## 阶段 0:DB 读取(每次对话开始前)

### 入口

`service.LoadAgentHistory`(agent_history.go:50)

### 干啥

从 `messages` 表拉最近 N 轮对话,重建成 `[]chat.Message` 喂给 Agent。

### 流程

1. `GetRecentMessagesBySession(sessionID, fetchLimit)` 拉原始消息行
   - `fetchLimit = maxRounds * 4`(每轮 ~2 行,放大 4 倍防漏)
   - 下限 50 行
2. 按 `RequestID` 配对成 (user, assistant) pair
3. 过滤掉不完整的 pair(没有 assistant 或 `IsCompleted=false`)
4. 按 `createdAt` 排序,取最近 `maxRounds` 轮
5. 每个 pair 展开成消息序列:
   - **user 消息**(`buildUserHistoryMessage`):用 `Content` + 图片 caption + 附件 prompt(不用 `RenderedContent`,那是旧格式)
   - **assistant 消息序列**(`buildAssistantHistoryMessages`):遍历 `AgentSteps`:
     - 每个 step 有非终止工具调用 → 输出 1 条 assistant(Thought + ToolCalls)+ N 条 tool 结果
     - 最后输出 1 条纯 assistant 消息(最终答案,剥掉 `</think> blocks)

### 关键点:历史工具结果在这一步就压缩了

`toolCallOutput`(agent_history.go:215)调 `agenttools.CompactToolOutputForHistory(tc.Name, tc.Result)` —— 按工具类型把结果压成元信息版:
- `search_results` 只留标题和 chunk_id
- `grep_results` 只留命中行
- `shell_exec` 只留 stdout 头尾
- 其他类型兜底压

这是**持久化压缩**,在 DB 读取时就做掉,不是 loop 里做。一次压缩,多次使用。

### 输出

`[]chat.Message`,顺序是 `[user, assistant, tool..., assistant, user, assistant, tool..., ...]`,不含 system prompt(系统提示词在 Agent 里加)。

## 阶段 1:消息拼装(进 loop 前)

### 入口

`buildMessagesWithLLMContext`(observe.go:843)

### 干啥

把 DB 读来的历史 + 当前用户问题,拼成 LLM 能吃的消息数组。

### 流程

1. 起手塞 system 消息:`{Role: "system", Content: systemPrompt}`
2. 处理 `llmContext`(DB 读来的历史):
   - 如果 `config.RetainRetrievalHistory == true` → 原样保留
   - 否则 → `redactHistoryKBResults(llmContext)` 把 **8 个 KB 工具的历史结果涂黑**:
     - `knowledge_search` / `grep_chunks` / `list_knowledge_chunks` / `query_knowledge_graph`
     - `get_document_info` / `wiki_search` / `wiki_read_page` / `wiki_read_source_doc`
   - 涂黑内容:`[Previous retrieval result omitted — knowledge base may have changed. Please perform a fresh search.]`
   - 跳过历史里的 system 消息(防注入)
3. 追加当前 user 消息:
   - `RenderUserTurnContent(sessionID, query)` 拼出 `<runtime_context scope="this_turn">` + `<must_use>` + query
   - `runtime_context` 含 current_time(日期级)/ session / 绑定 KB / pinned docs / 通信指令 / 答题指令

### 输出

`messages = [system, ...history, current_user]`

### 注意

这里 history 里的 tool 结果**已经被涂黑**(KB 工具)或**已经压缩过**(非 KB 工具,在 DB 读取阶段做的)。这是第一道"陈旧信息防护"。

## 阶段 2:ReAct Loop(每轮迭代)

### 入口

`executeLoop` → `runReActIteration`(engine.go:534)

每轮干 4 件事:**压缩 → Think → Analyze → Act/Observe**。这里只讲压缩那一步。

### 阶段 2.1:每轮开头的压缩检查

**位置**:engine.go:599-604

```go
currentTokens := e.estimateCurrentTokens(*messagesPtr)
managed, changed := e.manageContextWindow(ctx, *messagesPtr, round, currentTokens)
if changed {
    *messagesPtr = managed
    currentTokens = e.tokenEstimator.EstimateMessages(managed)
}
```

**`manageContextWindow`**(observe.go:39)干两件事:Compaction(主)+ trimToolResults(兜底)。

---

#### 闸 1:Compaction(主)

**触发条件**:`settings.ShouldCompact(currentTokens)`
- `Threshold = MaxContextTokens - ReserveTokens`(默认 Reserve 16384)
- 即:context 超过 `模型窗口 - 16K` 就触发

**流程**(`runCompaction` → `Compactor.Compact`):

##### 步骤 1:Prepare(找切点 + 分段)

`Prepare`(prepare.go:44):

1. `historyStart` 跳过 system(返回 1)
2. 从后往前找上一轮的 `MessageKindCompactionSummary` 消息,拿到 `previousSummary` 和 `boundaryStart`
   - 从这条之后开始切,不让摘要被再摘要(防"摘要的摘要的摘要")
3. `FindCutPoint` 找切点:
   - 从后往前累加 token,找最大的"保留尾部"使 `accumulated <= keepRecentTokens`
   - `keepRecentTokens` 默认 20000,上限 `usable / 4`(usable = MaxContext - Reserve)
   - 切点必须是合法切点(tool result 不能当切点,会被孤儿)
   - 如果切点落在 user 消息上 → 整 turn 切掉
   - 如果切点落在 turn 中间 → `IsSplitTurn = true`,记录 `TurnStartIdx`(这个 turn 的 user 消息位置)
4. 分两段:
   - `MessagesToSummarize` = 从 boundaryStart 到切点(要被摘要掉的)
   - `TurnPrefixMessages` = 如果 split turn,这个 turn 切点之前的部分(单独摘要)

**白话**:切点算法只看 token 预算,不看当前轮。turn 太大就 split turn,不豁免。

##### 步骤 2:buildSummary(调 LLM 生成摘要)

`buildSummary`(compactor.go:126):

1. 选指令:
   - 没有 `previousSummary` → `initialSummarizationInstructions`(从头写)
   - 有 `previousSummary` → `updateSummarizationInstructions`(在旧摘要基础上增量更新)
2. `buildSummarizationPrompt`:
   - 把对话包进 `<conversation>` 标签
   - 旧摘要包进 `<previous-summary>` 标签
   - 指令放最后(防 prompt injection 把对话文本当指令)
3. 调 `chatModel.Chat`:
   - `Temperature: 0.3`(事实性摘要,低温度)
   - `MaxTokens: summaryBudget`(reserve * 4/5,上限 keepRecentTokens)
   - `CacheRetention: CacheRetentionNone`(**摘要本身禁缓存**)
   - 最多重试 `maxSummarizationAttempts = 2` 次,每次 60s 超时
4. `validateSummary` 拒绝:
   - 空响应
   - 被 token cap 截断的响应(`length` / `max_tokens` finish reason)
5. 失败 fallback:用 `rawArchive`(原始对话文本)代替,标记 `degraded = true`

##### 步骤 3:SplitTurn 处理

如果切点把一个 turn 切两半:
- 额外调一次 `summarize` 生成 turn-prefix 摘要(用 `turnPrefixInstructions`,预算减半)
- 拼到 history 摘要后面,用 `splitTurnSeparator` 分隔

**白话**:turn 中间被切,前半段单独摘要,让保留的后半段有上下文。

##### 步骤 4:fileOps 追加

`prep.fileOps.format()` 把文件操作记录拼到摘要末尾。

##### 步骤 5:Apply(装配新消息数组)

`Apply`(prepare.go:97):
- `[system?, SummaryMessage, ...tail]`
- `SummaryMessage` 是 **user 消息**(`Role: "user", Kind: MessageKindCompactionSummary`)
- 内容包在 `<summary>...</summary>` 里
- 切点之后的 tail 原样保留

**白话**:摘要放 user 消息而非 system,不动 system prompt 保 cache;用 Kind 标记,下一轮能识别。

##### 步骤 6:minFreedFraction 检查

`runCompaction`(observe.go:100):
- `result.Freed() < TokensBefore / 20`(释放不到 5%)→ 标记 `compactionExhaustedAt = len(messages)`
- 本轮不再尝试
- 防止"摘要完只省一点点 → 下轮又触发 → 死循环"

---

#### 闸 2:trimToolResults(兜底)

**触发条件**:Compaction 完还超阈值,或者 Compaction 没东西可压。

**干啥**:`trimToolResultsToBudget`(observe.go:221):

1. 扫所有 `role == "tool"` 的消息,累加 token
2. 超过 `toolResultBudget`:
   - `toolResultBudget = MaxContextTokens / 5`(20%)
   - 下限 `minToolResultTokens = 8K`
   - 上限 `maxToolResultTokens = 32K`
3. 先把所有 tool 结果替换成 `compactedToolResultMarker`(只留字节数占位):
   ```
   [Tool result compacted: original_bytes=12345. Re-run the tool with narrower filters or a smaller range if more detail is needed.]
   ```
4. 然后**从最新往最旧**用剩余预算"赎回"完整结果:
   - 能塞下完整 → 还原完整
   - 塞不下 → `compactToolMessage` 二分查找最大 head/tail 预览(头 1/4 + 尾 3/4)

**关键**:**只裁 tool 结果,不动 assistant 和 user**。assistant 的 ToolCalls 原样保留,保证 OpenAI 要求的 tool_call/tool_result 配对不拆。

**白话**:兜底是"留壳去瓤"——保留工具被调用过的事实(壳),丢具体内容(瓤),配对不拆。

---

### 阶段 2.2:Think(调 LLM)

`callLLMWithRetry` 调 LLM,拿响应。

---

### 阶段 2.3:Overflow 恢复(独立路径)

**位置**:engine.go:633-648

```go
if !e.overflowRecovered && e.responseHitContextLimit(resp) {
    e.overflowRecovered = true
    *messagesPtr = e.forceCompaction(ctx, *messagesPtr, round)
    resp, err = e.callLLMWithRetry(...)  // 重试一次
}
```

**`responseHitContextLimit`**:判断响应是不是因为 context 满了被截断(finish_reason = length 且 completion 远低于请求的 budget)。

**`forceCompaction`**(observe.go:171):
- 跟 `runCompaction` 一样,但 `reason = ReasonOverflow`(不检查阈值,强制压)
- 压不动 → 调 `trimToolResults` 兜底

**`overflowRecovered` 标志**:**每轮只恢复一次**。如果恢复后还溢出,说明问题不是历史大小,不再重试。

**白话**:以前超限就崩,现在超限就强行压缩再试一次,但只试一次。

---

### 阶段 2.4:Analyze + Act/Observe

- `analyzeResponse` 判断是否停止(natural stop / content_filter / emptyContent)
- 不停 → `appendToolResults`(observe.go:741)把本轮工具结果追加进 messages:
  - 加 assistant 消息(Thought + ToolCalls)
  - 加 tool 消息(每个工具结果)
  - 如果含 markdown 图片,末尾追加 user 消息提醒(不动 system,保 cache)
- 下一轮循环回到阶段 2.1

---

## 阶段 3:Loop 结束

### 触发条件

- `analyzeResponse` 返回 `isDone = true`(natural stop / content_filter)
- 检测到 stuck loop(连续 3 次同样内容)
- `ctx.Err()`(用户按 stop)
- 达到 `MaxIterations`(如果配置了有限值,新版默认 -1 无限)

### 结束后

state 带 `RoundSteps` / `FinalAnswer` 返回,由上层 service 持久化到 DB 的 `messages` 表(assistant 消息 + AgentSteps)。

### 注意

loop 结束**没有额外的压缩步骤**。压缩都发生在 loop 内部每轮开头(阶段 2.1)和 overflow 恢复(阶段 2.3)。下一轮对话开始时,阶段 0 的 `LoadAgentHistory` 从 DB 重新读历史,再走一遍 `CompactToolOutputForHistory` 持久化压缩。

## 关键设计决策(串联起来看)

| 决策 | 在哪 | 为啥 |
|---|---|---|
| **历史工具结果在 DB 读取时就压缩** | `LoadAgentHistory` → `CompactToolOutputForHistory` | 一次压缩,多次使用;不在 loop 里反复压 |
| **KB 工具结果额外涂黑** | `redactHistoryKBResults` | KB 可能被改/切/删,历史结果不可信,逼模型重新检索 |
| **摘要放 user 消息** | `SummaryMessage` | 不动 system,保 cache;且 user 消息也喂给 LLM,信息不丢 |
| **摘要用 Kind 标记** | `MessageKindCompactionSummary` | 下一轮 Prepare 能识别"这是上轮摘要",增量更新而非重摘要 |
| **切点不参考当前轮** | `FindCutPoint` | 当前轮相关性高不能切;turn 太大就 split turn,不豁免 |
| **摘要本身禁缓存** | `CacheRetention: None` | 摘要是中间态,下次用不上,缓存浪费钱 |
| **5% 防无效摘要** | `minFreedFraction` | 摘要完只省一点 → 标记 exhausted,本轮不再试 |
| **overflow 每轮只恢复一次** | `overflowRecovered` 标志 | 恢复后还溢出 = 问题不是历史大小,重试无意义 |
| **trimToolResults 只动 tool 结果** | `trimToolResultsToBudget` | 保 assistant 的 ToolCalls,保 OpenAI 配对不拆 |

## 跟旧版(笔记 27)的心智差异

**旧版心智**:4 道闸层层过滤,每道管一类。
**新版心智**:**两个时间点 + 两种手段**。

### 两个时间点

1. **对话开始前**(DB 读取 + 拼装)—— 持久化压缩 + 涂黑
   - `LoadAgentHistory` 里 `CompactToolOutputForHistory`
   - `buildMessagesWithLLMContext` 里 `redactHistoryKBResults`
2. **每轮开头**(loop 内)—— Compaction + trimToolResults 兜底
   - `manageContextWindow` 在 engine.go:599 调用

### 两种手段

1. **压缩**(CompactToolOutputForHistory / trimToolResults)—— 按规则裁,丢内容保元信息
2. **摘要**(Compaction)—— 调 LLM 生成结构化摘要,保语义丢细节

旧版把"压缩"和"摘要"拆成 4 道闸,新版合并成"开始前压一次 + 每轮摘要一次 + 兜底裁一次"。
