# 22 · 向量化与入库全流程(清理旧数据 → 建 DB Chunk → 写 chunks 表 → 建 IndexInfo → BatchIndex → 异步后处理 → 状态机)

> 阶段 3,之前讲过未落盘,现结合代码完整落盘。核心:chunks 表 ALWAYS 写;向量化内容 = 文档标题 + 面包屑 + 正文(3 层拼接);parent 不进向量库;入库后还有一整套异步后处理 + 一个隐藏的"二次 BatchIndex"。

---

## 一句话

> **`processChunks` 是入库主函数:先清理旧数据(幂等),再把切块产物建成 DB Chunk(父块先建拿真 ID,子块挂 ParentChunkID)写入 chunks 表(Always 写,即使关向量库),然后把只有子块的 textChunks 拼成 3 层 IndexInfo(标题+面包屑+正文trim),经 BatchIndex 批量 embed 写向量库。入库成功后状态置 processing,入队一个 KnowledgePostProcess 编排任务,异步 fan-out 摘要/问题/图谱/wiki——其中问题生成会再做一次 BatchIndex(把生成的问句也建索引,question-based 检索)。**

## ① 幂等清理:删旧数据(L276-303)

入库前先把这份知识的旧痕迹全清掉,保证幂等(重新处理同一文档不重复):

```go
// L279 删旧 chunks
s.chunkService.DeleteChunksByKnowledgeID(ctx, knowledge.ID)
// L289 删旧向量索引
retrieveEngine.DeleteByKnowledgeIDList(ctx, []string{knowledge.ID}, embeddingModel.GetDimensions(), knowledge.Type)
// L299 删旧知识图谱
s.graphEngine.DelGraph(ctx, []types.NameSpace{namespace})
```

**三处都"不返回错误,继续处理"**(L280/L290/L300 注释:may not exist)——可能本来就没旧数据,删失败不该阻断新数据入库。这是幂等设计:重跑不会脏数据。

## ② 三个中断检查点(为什么是 3 次)

`processChunks` 全程插了 3 个 `isKnowledgeAborted` 检查,这是你笔记里提到的"3 个中断检查点":

| 检查点 | 位置 | 时机 | 行为 |
|--------|------|------|------|
| #1 | L257 | 刚进入,还没干任何事 | 直接 return,啥都不做 |
| #2 | L468 | DB Chunk 建好但**还没写库** | 直接 return(啥都没持久化) |
| #3 | L556 | chunks 已写库,**BatchIndex 前** | deleting→删掉刚写的 chunks;cancelled→保留数据 return |
| (成功后) | L600 | BatchIndex 已成功 | deleting→清理 chunks+索引;cancelled→保留 return |

**为什么查这么多次**:知识处理是长任务(大文档 embed 要几十秒),用户可能中途删/取消。每查一次,如果已写库就按 deleting/cancelled 区别处理——**deleting 是要删,连已写数据一起清;cancelled 是要停但保留已写数据**。这是"长任务可中断"的标准做法,不是冗余。

## ④ ⑤ 写 chunks 表:Always 写(L479)

```go
// L479
s.chunkService.CreateChunks(ctx, insertChunks)
```

**这是最重要的一句,也是 README 那句"chunks 表 ALWAYS 写"的出处。**

关键在注释(L473-475):
```go
// Save chunks to database — ALWAYS, regardless of indexing strategy.
// Chunks are needed for wiki generation, graph extraction, and summary generation
// even when vector/keyword indexing is disabled.
```

**即使知识库关了向量/关键词索引(只开 wiki/图谱/摘要),chunks 表也必须写。** 因为:
- 知识图谱抽取读 chunks 表(不回源文档)
- 摘要生成读 chunks 表
- wiki 生成读 chunks 表

**所以 chunks 表是"事实库",向量库是"检索索引"——两者分离。** chunks 表是后面所有异步后处理的输入源。这解释了为什么 quota 不足/BatchIndex 失败时,代码要专门回滚已写的 chunks——因为 chunks 已写但向量没建,状态不一致。

## ⑥ ⑦ 建 IndexInfo:3 层拼接(L513-528)

这是本篇重点之一。只对 `textChunks`(只有子块,父块已被 L449 的 `if ChunkType==Text` 过滤掉)建索引:

```go
// L513-528
indexInfoList := make([]*types.IndexInfo, 0, len(textChunks))
for _, chunk := range textChunks {
    indexContent := buildKnowledgeIndexContent(knowledge, chunk.EmbeddingContent())
    indexInfoList = append(indexInfoList, &types.IndexInfo{
        Content:    indexContent,   // ← 拼好的3层文本
        SourceID:   chunk.ID,
        ChunkID:    chunk.ID,
        KnowledgeID, KnowledgeBaseID, IsEnabled...
    })
}
```

### 3 层拼接从外到内

```
┌──────────────────────────────────────────────────┐
│ 第1层(最外): 文档标题 knowledge.Title            │ 用 "\n" 连接
│   buildKnowledgeIndexContent (knowledge_index_content.go:20) │
├──────────────────────────────────────────────────┤
│ 第2层(中): 面包屑 ContextHeader(Markdown标题路径) │ 用 "\n\n" 连接
│   Chunk.EmbeddingContent (chunk.go:209-210)      │
├──────────────────────────────────────────────────┤
│ 第3层(最内): 正文 Content(已 TrimSpace)          │
│   chunk.go:206                                   │
└──────────────────────────────────────────────────┘
```

**展开形态**:`<文档标题>\n<面包屑>\n\n<正文trim>`

### 三个关键细节

**1. 标题和面包屑分隔符不一样**:标题→面包屑用**单个 `\n`**(knowledge_index_content.go:20),面包屑→正文用**双个 `\n\n`**(chunk.go:210)。有意区分层级——标题是文档级(紧贴),面包屑是章节级(段间留白)。

**2. 为什么 Content 要 TrimSpace**(chunk.go:206):Content 是原文 rune 区间切下来的,边界常切在换行处,带首尾多余空行。这些空白会**稀释 embedding 向量 + 浪费 token**,所以 embedding 时 trim 掉首尾。**但 Content 字段本身不改**(只 trim 给 embedding 用的临时副本),保持 `End-Start == len(Content)` 位置不变量。

**3. 文档标题 vs 面包屑不是同一个东西,不重复**:
- `knowledge.Title` = 知识条目的**文档级标题**(元数据,Knowledge 表,整篇共享一个,外部给)
- `ContextHeader` = 文档**内部章节标题的层级路径**(面包屑,如`# 第一章\n## 1.2 方法\n`),切块时 Tier1 heading 切分器从正文 Markdown 标题结构提取(heading_splitter.go:72-115),逐 chunk 不同

两者来源不同、语义不同、加在不同层,互不重叠。最终 embedding 文本同时含两者,构成完整 3 层上下文。

**4. custom metadata 不进 embedding**(knowledge_index_content.go:9-11 注释):metadata 只在文档级喂给回答模型/摘要模型一次,不每个 chunk 重复——避免稀释向量 + 省存储。

### 父块为什么不进 indexInfoList

L445-452 过滤:
```go
textChunks := make([]*types.Chunk, 0, len(chunks))
for _, chunk := range insertChunks {
    if chunk.ChunkType == types.ChunkTypeText {  // 只收 Text
        textChunks = append(textChunks, chunk)
    }
}
```
父块 `ChunkType=ParentText` 被过滤,不进 textChunks → 不进 indexInfoList → 不 embed → 不进向量库。父块只写 chunks 表(供检索时拉上下文用)。**靠 ChunkType 区分进不进向量库,这是笔记 20 已讲的,这里是代码确认。**

## ⑧ 存储配额检查(L531-551)

BatchIndex 前先估存储,防超配额:

```go
totalStorageSize = retrieveEngine.EstimateStorageSize(ctx, embeddingModel, indexInfoList)
if tenantInfo.StorageQuota > 0 {
    if tenantInfo.StorageUsed+totalStorageSize > tenantInfo.StorageQuota {
        knowledge.ParseStatus = types.ParseStatusFailed
        knowledge.ErrorMessage = "存储空间不足"
        return  // 不进 BatchIndex
    }
}
```

**EstimateStorageSize 不真调 embedding API**(keywords_vector_hybrid_indexer.go:298-314):只按维度生成**占位零向量**估算字节数,不花钱。

**quota 不足会怎样**:直接 return,不调 BatchIndex;knowledge 标失败;**已写的 chunks 不回滚**(此时还没到失败回滚逻辑);不实际占用配额。`StorageQuota<=0` 表示不限制,跳过。

## ⑨ BatchIndex:批量 embed + 写向量库(L566)

```go
err = retrieveEngine.BatchIndex(ctx, embeddingModel, indexInfoList)
```

这是本篇另一重点。调用链:

```
knowledge_process.go:566  retrieveEngine.BatchIndex
   └─ composite.go:212  CompositeRetrieveEngine.BatchIndex  (按SourceID去重 + 并发分发所有子引擎)
        └─ keywords_vector_hybrid_indexer.go:87  KV...BatchIndex  (按retrieverType)
             ├─ 含Vector分支:
             │   1. sanitizeForEmbedding:剥离inline base64图片→[image],超长截断20000rune (L159-175)
             │   2. batchEmbedWithBackoff:带指数退避重试5次(200/400/800/1600/3200ms) (L131-153)
             │      → embedder.BatchEmbedWithPool:按BATCH_EMBED_SIZE(默认5)分批→ants协程池并发→model.BatchEmbed(HTTP)
             │   3. 切批40 → concurrentBatchSave → indexRepository.BatchSave(params["embedding"])
             └─ 仅Keyword分支:
                 切批10 → concurrentBatchSaveNoEmbedding → BatchSave(无embedding)
```

### 5 个要点

**1. 是批量+并发,不是单条**:`BatchEmbedWithPool`(batch.go:27-104)把整个 contentList 按 BATCH_EMBED_SIZE(默认5)切子批,丢进 ants 协程池并发,每个子批一次 HTTP(BatchEmbed 接口)。一条 HTTP 请求处理多条文本,省往返。

**2. 带指数退避重试**:embed 可能限流/超时,重试 5 次(200→3200ms),总等约 6 秒。这是 embedding API 调用的韧性设计。

**3. 内容清洗 sanitizeForEmbedding**(L159-175):两步——①正则把 inline base64 图片替换成 `[image]`(图片数据不该进 embedding,浪费且污染向量)②超长内容截断到 20000 rune(防超 embedding API 输入上限)。**注意:这是 BatchIndex 层的清洗,在 3 层拼接之后。**

**4. 向量怎么存**:经 `additionalParams["embedding"]`(map[SourceID][]float32)传入各 backend 的 BatchSave。PostgreSQL 存 `pgvector.HalfVector`(fp16 半精度,省一半存储,structs.go:27),Elasticsearch 存 `[]float32`。**向量库和关键词库存在同一张表/同一行文档**,向量在 Embedding 列,关键词检索只读 Content 列——字段级分离,不是表级。

**5. 失败回滚**(L566-593):BatchIndex 失败→knowledge 标失败→**删已写 chunks**(回滚 DB)→**DeleteByKnowledgeIDList**(回滚向量库可能部分写入的)→failStage(StageEmbedding)。因为 concurrentBatchSave 可能部分批成功部分失败,按 knowledgeID 整体清。错误码区分"向量库写失败"vs"embedding 限流"(isLikelyRateLimitError)。

### 向量库 vs 关键词库:取决于 retrieverType

开关是 `kb.NeedsEmbeddingModel()`(VectorEnabled || KeywordEnabled 任一为 true 就需要 embedding 模型)。实际是否生成向量看 `retrieverTypes` 是否含 `VectorRetrieverType`:

| KB 配置 | 生成向量? | 行为 |
|---|---|---|
| 只 VectorEnabled | ✅ | embed + 写向量列 |
| 只 KeywordEnabled | ❌ | 不 embed,只写 content/元数据,靠全文检索 |
| 两者都开 | ✅ | 一次 embed,向量+content 同写一行,关键词检索复用 content 列 |
| 都不开(只wiki/graph) | — | L617 skipStage,根本不调 BatchIndex |

**注意**:`CapVector`/`CapKeyword`(capabilities.go:24-25)是 agent 工具层的能力标记(判断 KB 能否支撑 knowledge_search 工具),**不是索引写入开关**。索引层开关是 `IndexingStrategy.NeedsEmbedding()`。

## ⑩ ⑪ ⑫ 入库后的异步后处理 + 状态机

这是 README 没提、但代码里很大的一块。**入库成功 ≠ 知识可用。**

### 状态机三态(关键)

```
processing → finalizing → completed
   ↑入库成功置此    ↑编排器SetFinalizing   ↑FinalizeSubtask计数归零
```

- `processing`:入库成功后置(L627 finalizeIndexedKnowledgeState)。**不直接置 completed**——因为摘要/问题/图谱还没跑。
- `finalizing`:`KnowledgePostProcess` 编排器把 processing→finalizing + 写 `pending_subtasks_count=N`(knowledge.go:639-649,原子)。**这是同步解析与异步富化之间唯一的持久化交接点。**
- `completed`:`FinalizeSubtask`(repository/knowledge.go:571-628)每完成一个子任务计数 -1,**归零才提升为 completed**,且 WHERE 守卫防 cancel/delete 被晚到的 promote 覆盖。

**为什么三态**:把"同步解析"和"异步富化"干净切开,避免"入库成功就 completed、但摘要还在跑"的假完成。代价是计数器必须严丝合缝——代码里大量 shortfall 对账(knowledge_post_process.go:431-462)在还这个复杂度的债。

### 入队:只入队一个编排任务

`processChunks` 成功后只入队 **一个** `TypeKnowledgePostProcess`(L662-664),真正的 fan-out 在 `KnowledgePostProcessService.Handle`(knowledge_post_process.go:78)异步展开。

### 编排器 fan-out(全部异步,asynq 独立 worker 池)

| 任务 | 入队点 | 队列 | 干啥 |
|------|--------|------|------|
| 摘要 Summary | post_process.go L353 | QueueSummary | 给文档生成摘要 |
| 问题生成 Question(按批) | L376 | QueueQuestion | **每批再做一次 BatchIndex**(见下) |
| 知识图谱 Graph(按chunk) | L384-393 | QueueGraph | 读chunks表抽节点/关系写Neo4j |
| Wiki 摘要入库 | L402 | QueueWiki | wiki_ingest.go:531 |
| 自动打标签 AutoTag | L346 | QueueSummary | best-effort,不占finalizing计数 |

### ★ 隐藏的二次 BatchIndex:问题生成

**这是只读 processChunks 会漏掉的关键点。** 问题生成 `processQuestionGenerationForChunks`(knowledge_process.go:1756-2074):

1. L1956 按 ChunkIDs 从 DB 读回 batch chunks
2. L2005 调 LLM 为每个 chunk 生成问题(带前后邻居上下文)
3. L2037 问题写进 chunk 的 GeneratedQuestions 并 UpdateChunk
4. **L2048-2058 为每个问题构造 IndexInfo,Content=buildKnowledgeIndexContent(knowledge, gq.Question)**
5. **L2062-2069 第二次 retrieveEngine.BatchIndex**——把生成的问句也 embed 写向量库

**为什么**:用户用自然问句查询时,原文是陈述句,和问句的向量分布有 gap。预生成问句并独立建索引,等于为每个 chunk 额外构造一组"问题锚点"向量,`SourceID` 仍指向原 chunk。这是 **question-based 离线预生成检索增强**,比在线改写查询更稳定。

**所以向量库实际被写两次**:processChunks 的主 BatchIndex(原文)+ 问题生成批次的二次 BatchIndex(问句)。每批(20 chunks/batch)一次向量库写入。

### 知识图谱抽取:读 chunks 表,不回源文档

`ExtractChunk`(extract.go:230-407):
- L297 `chunkRepo.GetChunkByID` 从 **chunks 表**读回单个 chunk
- L354 `extractor.Extract(ctx, chunk.Content)` 喂 LLM 抽节点/关系
- L367 `graphEngine.AddGraph` 写 Neo4j,节点挂 `Chunks=[]string{chunk.ID}` 回指源 chunk

**按 chunk 粒度、读已落库的 chunk.Content,不回源文档。** 这就是为什么 ⑤ chunks 表必须 Always 写——图谱抽取直接消费它。前置门:`NEO4J_ENABLE != "true"` 则不入队(extract.go:99-102)。

### 处理阶段:5 段进度时间线

5 个阶段常量(knowledge_span.go:42-48),前端时间线来源:

```
DocReader → Chunking → Embedding → Multimodal → PostProcess
```

DAG 依赖(StageDependencies L70-76):Chunking 依赖 DocReader;Embedding 和 Multimodal 都依赖 Chunking(二者独立);PostProcess 依赖 Embedding+Multimodal。**某阶段 fail 级联 cancel 下游**。

四方法(knowledge.go:253-298)写 `knowledge_processing_spans` 表:
- `beginStage`:开 running span(记 started_at)
- `endStage`:写 output+duration,状态 done
- `failStage`:写 error_code/message,状态 failed,**级联 cancel 下游**
- `skipStage`:状态 skipped(如纯文本文档跳过多模态 L649)

在 processChunks 的分布:Chunking(L476/L492/L484)、Embedding(L508/L595/L590/**L618 skip**)、Multimodal(L642 begin/L649 skip)。PostProcess 在编排器里标(post_process.go:109/475)。

## 两个容易忽略的认知(你应该带走的)

### 1. chunks 表是事实库,向量库是检索索引——两者分离

chunks 表 ALWAYS 写,向量库只在开向量/关键词索引时写。图谱/摘要/wiki 都直接读 chunks 表,不读向量库、不回源文档。**所以"入库"其实分两层:落事实(chunks 表)+ 建索引(向量库)。** BatchIndex 失败回滚的是向量库,但 chunks 表已写——这就是为什么回滚逻辑要专门删 chunks。

### 2. 向量库实际被写两次(主+问题),不是一次

只读 processChunks 会以为向量库写一次。实际:主 BatchIndex 写原文向量 + 问题生成批次再写问句向量。后者是 question-based 检索增强,问句和原文是两种语义分布,各建一组向量锚点。**这是 WeKnora 检索精度的隐藏来源之一。**

## 你应该带走的 7 件事

1. **`processChunks` 是入库主函数**:12 步,从清理旧数据到入队后处理。3 个中断检查点防长任务中途被删/取消,deleting 清数据 cancelled 保留数据。

3. **向量化内容 3 层拼接**:`文档标题\n + 面包屑\n\n + 正文(已trim)`。标题是文档级(knowledge.Title),面包屑是章节级(Tier1切时从Markdown标题提取),不重复。custom metadata 不进 embedding(文档级喂一次,避免稀释)。
