# 21 · 父子分块优化分析:父块强塞噪声、检索双路径、为什么不推荐 LLM 摘要

> 用户问:父子分块启用后,所需内容若只在某 1-2 个子块里够用,其余父块内容是不是无用且白占 token?能不能入库时给父块调 LLM 生成摘要,检索时带"摘要+命中子块",并告诉模型可用工具按需拉全上下文,让它选择性获取而非强塞?

---

## 一句话

> **用户诊断对——父子分块的自动检索路径确实"强塞父块",父块其余内容是潜在噪声 + token 浪费。但用户的"按需拉取"设想项目已实现(在 Agent 工具路径,不在自动路径);而"父块 LLM 摘要"方案不推荐——摘要丢不可预测的信息、入库即烧 token、治标不治本。真要优化,从轻到重:①父块按标题边界自适应切(0 成本,最该先做)②自动路径父块截断成窗口 ③自动路径也改延迟拉取。**

---

## 一、用户的诊断:完全正确

> 「所需内容只在某 1-2 个 child 里够用,其余父块内容是无用的,还额外占 token」

这就是笔记 20 写的「代价 3:父块带入相邻话题噪声」。父块 4096 强塞给 LLM,不管命中的 384 字在父块哪个角落,其余 ~3712 字都是潜在噪声。**这个痛点成立。**

---

## 二、用户低估的关键事实:WeKnora 有两条并行检索路径

用户只在"自动检索"那条上想优化,漏了 WeKnora 其实有两条并行的检索链路。

### 路径 A:自动向量检索(merge.go 强塞父块)

`resolveParentChunks`(merge.go:218)做的:

```go
// 检索命中子块 → 无条件拉父块 → 拼上 → 强塞给 LLM
parent := parentMap[r.ParentChunkID]
r.Content = JoinChunkContent(parent.Content, r.Content, "\n\n")
```

**这里父块是强塞的,用户的痛点在这里成立。** 命中子块必带整个 4096 父块,不问 LLM 需不需要。同父去重(merge.go:240 map 收集 ParentChunkID)只防"多个子块拉同一父块重复",不防"父块其余内容是噪声"。

### 路径 B:Agent 工具按需拉取(list_knowledge_chunks / grep_chunks)

WeKnora 的 Agent **本来就有"按需拉 chunk"的工具**,且工具输出**带 `parent_chunk_id` 字段**:

```go
// list_knowledge_chunks.go:225
chunkData := map[string]interface{}{
    ...
    "parent_chunk_id": c.ParentChunkID,   // ← 父块 ID 也给模型
}
```

**用户想要的"告诉模型可按需获取全上下文"——Agent 路径已经在做。** Agent 拿到命中子块 + parent_chunk_id,自己决定要不要再调工具拉父块。**这条路径天然不强塞,用户想要的能力已存在。**

### 两条路径对比

| 维度 | 路径 A 自动检索 | 路径 B Agent 工具 |
|------|----------------|------------------|
| 父块获取 | 无条件强塞 | 模型按需拉(可选) |
| 父块形态 | 原文全量 4096 | 输出带 parent_chunk_id 标记 |
| token | 父块必占 | 只在模型判断需要时占 |
| 噪声风险 | 高(父块全塞) | 低(模型自选) |
| 延迟 | 低(一次拼好) | 可能多轮(模型决定→拉→答) |
| 质量 | 上下文全但含噪声 | 依赖模型判断力 |
| 代码 | merge.go:317 | internal/agent/tools/list_knowledge_chunks.go:225 |

**用户设想的"按需拉取"= 路径 B,项目已实现。** 用户的痛点只存在于路径 A。

---

## 三、用户的"父块 LLM 摘要"方案:三盆冷水

用户核心创新:入库时给父块调 LLM 生成摘要,检索时带"摘要+命中子块"。思路新颖,但有三个硬问题。

### 冷水 1:摘要丢信息,且丢的是"不可预测"的信息

LLM 生成摘要时不知道用户**将来**问什么。父块 4096 字讲"安装/配置/启动/排错"四件事,摘要可能重点写"安装"而压缩"排错"。结果用户问排错,摘要信息不够,还得回头拉原文——**省了 token,但多了一次往返**。

摘要的本质是"用信息损失换 token 节省",这个交易在"问题未知"时是亏的。RAG 入库阶段根本不知道检索问题,摘要无法针对性保留。

### 冷水 2:摘要要花成本,且入库时就要花

4096 父块的摘要要调一次 LLM。知识库几千个父块 = 入库时几千次 LLM 调用。**把"检索时省 token"的成本前置到"入库时烧 token"**,且摘要质量直接决定后续检索质量,入库错了以后改不动。一次性写入成本变成"每文档必付"的固定开销。

### 冷水 3:摘要治标不治本

用户最初的问题是"父块里其他话题是噪声"。摘要如果是全话题摘要,照样包含其他话题;如果只摘命中的,又回到"不知将来问什么"。**摘要无法解决"父块跨话题噪声"的根本,根本解是"让父块更小"或"按需拉取"。**

---

## 四、真正能优化痛点的 3 个方向(从轻到重)

按"改动量 / 收益 / 风险"排序。

### 方向 1(最轻,推荐先做):父块 size 自适应,而非写死 4096

现在父块固定 4096(DeriveParentChildConfigs strategy.go:220)。但父块该多大应跟**文档结构**走:
- 技术文档标题密集,4096 跨好几个 H2 标题 → 跨话题
- 小说段落松散,4096 可能就一个场景 → 不跨

**让父块在"标题边界"处封口,而非凑满 4096**,从源头减少跨话题。笔记 20 讲的"每层独立体检选刀"已支持这个(Strategy 传 Tier1 heading 切),只是父块 size 还是定值。改成"父块优先按 H1/H2 切,4096 只是上限"就能降噪,**零额外 token 成本,零 LLM 调用**。

收益:从源头消除"父块跨多个话题"的最大噪声源。
风险:极低,只是切分参数从定值变自适应。

### 方向 2(中等):给自动路径加"父块截断"而非全塞

现在 `resolveParentChunks` 是整个 4096 父块拼上(merge.go:340)。改成"**只取命中子块在父块里的前后 N 字上下文窗口**",而非整个父块:

```
命中子块在父块 2000~2384 字处
→ 只取 1800~2584 字窗口(前 200 后 200)
→ 保留局部上下文,砍掉远端噪声
```

这是"滑动窗口"思路,**比摘要便宜得多**(纯字符串切片,不用 LLM),且不丢命中点附近信息。

收益:自动路径父块从"全量强塞"变"局部窗口",降噪 + 省 token,且不调用 LLM。
风险:窗口外的相关内容会丢(如果问题答案恰在远端),需调 N。窗口太小丢上下文,太大退回原状。

### 方向 3(最重,最贴用户设想):自动路径也改延迟拉取

用户的"让模型选择性获取"——把自动检索也改成:
1. 先只给 LLM 命中子块 + 父块"定位标记"(parent_chunk_id + 父块首句预览)
2. LLM 觉得上下文不够,**主动调 list_knowledge_chunks 工具拉父块**
3. 拿到再答

跟用户设想几乎一致,且工具已存在(路径 B 的工具)。

收益:自动路径不再强塞,模型按需,token 最省。
风险:
- **每次问答可能多一轮 LLM 调用**(模型决定要拉→拉→再答),延迟翻倍
- **依赖模型判断力**——判断错了不拉,答错;判断对了省 token
- 自动路径的"低延迟"优势丢失,退化成路径 B 的行为

---

## 五、3 个方向对比

| 方向 | 改动量 | 额外 token | 延迟 | 降噪效果 | 风险 |
|------|--------|-----------|------|---------|------|
| ① 父块按标题自适应切 | 小 | 0 | 不变 | 中(源头减少跨话题) | 低 |
| ② 自动路径父块截断窗口 | 中 | 0 | 不变 | 中高(砍远端噪声) | 中(窗口外内容可能丢) |
| ③ 自动路径延迟拉取 | 大 | -1轮(省)| 翻倍 | 高(按需) | 高(依赖模型判断) |
| (用户原方案)父块 LLM 摘要 | 中 | 入库烧/检索省 | 不变 | 低(治标) | 高(丢信息不可预测) |

**工程判断:先做方向 1。** 父块写死 4096 是当前最该改的点——它从源头制造跨话题噪声,而体检机制已具备"按标题切"能力,只是没对父块启用。这一步做完,用户说的"父块无用内容"问题能消掉一大半,且不花一个 token、不引入摘要的不确定性。

## 六、关键认知:RAG 优化的两条铁律

这次分析暴露了两个容易踩的优化陷阱,记下来:

### 铁律 1:入库阶段不知道检索问题,不能做"针对性"优化

用户的 LLM 摘要方案踩的就是这条。入库时父块摘要不知道将来问什么 → 摘要无法针对性保留 → 丢不可预测信息。

**凡是"入库时预决定检索质量"的优化(摘要、预生成 QA、关键词预提取),都要警惕"问题未知"这个根本约束。** 它们能做的只有"通用压缩",而通用压缩必然丢信息。

### 铁律 2:省 token 的代价总要转移到别处

- 摘要省检索 token → 转移到入库烧 token + 丢信息
- 延迟拉取省 token → 转移到延迟翻倍 + 依赖模型判断
- 截断窗口省 token → 转移到可能丢远端内容

**没有免费午餐。** 优化是把代价从一处挪到另一处,关键是挪到"你能接受的那处"。方向 1 之所以推荐,是因为它的代价是 0——它不是"挪代价",是"从源头减少问题产生"。
