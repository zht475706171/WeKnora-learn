# 笔记 39 · 压缩粒度阶梯(从细到粗四级)

> 接笔记 37(压缩流程完整链路)+ 笔记 38(优化点)。
> 本篇把散落在各处的压缩机制抽象成"粒度阶梯"框架:从最细的单工具结果,
> 到最粗的全量历史摘要,一共四级,每级管一层。
>
> 风格延续:专业术语 + 白话解释双轨。

---

## 一句话总结

WeKnora 的压缩不是一个机制,是**四级粒度阶梯**:
细(单工具结果按类型裁)→ 细+(跨 turn KB 结果强制涂黑)→ 中(保留区 tool 消息按预算裁)→ 粗(全量历史摘要替换)。
每级作用域不同、动机不同、触发条件不同,层层递进,从"省 token"到"防陈旧"到"兜底"。

---

## 一、四级阶梯总览

| 级 | 机制 | 时机 | 作用域 | 动机 | 跟内容大小有关吗 |
|---|---|---|---|---|---|
| ①细 | `CompactToolOutputForHistory` | 读 DB 时(LoadAgentHistory) | 单个工具结果 | 省 token(裁成元信息) | 有关,按类型裁 |
| ②细+ | `redactHistoryKBResults` | 装配时(buildMessagesWithLLMContext) | 历史 turn 的 8 个 KB 工具结果 | **防陈旧**(KB 可能被改) | **无关,强制涂黑** |
| ③粗 | 闸 1 `Compaction` | loop 每轮开头,超阈值 | 切线以前的全部历史 | 省 token(摘要替换) | 有关,超阈值触发 |
| ④中 | 闸 2 `trimToolResults` | Compaction 残局兜底 | 保留区内**所有** tool 消息 | 省 token(按预算裁) | 有关,合计超窗口/5 |

**注意排序**:阶梯是按粒度排(细→粗),但执行顺序是 ①② 进 loop 前,③④ 在 loop 内。

---

## 二、每级细讲

### 级 ①:单工具结果压缩(最细)

**位置**:`LoadAgentHistory` → `toolCallOutput`(agent_history.go:215)→ `agenttools.CompactToolOutputForHistory`

**白话**:DB 里存的是工具执行时的原始结果(基本全量),读取那一刻按工具类型裁成元信息版:
- `search_results` 只留标题和 chunk_id
- `grep_results` 只留命中行
- `knowledge_chunks_list` 只留清单
- `shell_exec` 只留 stdout 头尾
- 其他类型兜底压

**特点**:
- 在**读取路径**上做,不在入库时做(DB 保留全量真相)
- 压完的版本只存在于本次请求内存,不回写 DB
- 一次压缩多次使用(每个 turn 读历史都会走一遍)

### 级 ②:跨 turn KB 结果涂黑(细+,最容易被忽略的一级)

**位置**:`buildMessagesWithLLMContext`(observe.go:843)→ `redactHistoryKBResults`(observe.go:825)

**白话**:历史 turn 里 8 个 KB 工具(knowledge_search / grep_chunks / list_knowledge_chunks / query_knowledge_graph / get_document_info / wiki_search / wiki_read_page / wiki_read_source_doc)的结果,不管多大,一律换成:

```
[Previous retrieval result omitted — knowledge base may have changed. Please perform a fresh search.]
```

**特点**:
- **动机不是省 token,是防陈旧**:KB 可能被编辑/切换/删除,历史里的检索结果现在可能就是错的,不涂黑模型会拿旧数据回答
- 强制涂黑,不分大小
- 开关:`config.RetainRetrievalHistory == true` 时跳过(保留完整检索历史)
- "留壳去瓤":保留工具被调用过的事实(壳),丢具体内容(瓤),配对不拆

### 级 ③:全量历史摘要(最粗)

**位置**:`manageContextWindow` → `runCompaction` → `Compactor.Compact`(笔记 37 阶段 2.1 详讲)

**白话**:估算超过 `窗口 - 16K` 触发。从队尾往回圈 2 万 token(KeepRecent)画切线,切线以前的历史调 LLM 摘要成 8 栏交接表(Goal / Constraints / Progress / Key Decisions / Next Steps / Critical Context),替换原文。切到轮中间就 split turn 给前半段单独做"前情提要"。

**特点**:
- 花一次 LLM 调用的钱,保语义丢细节
- 摘要作为 user 消息塞回(不动 system 保 cache),带 Kind 标记支持增量更新
- 5% 验收:释放不够不认账
- 摘要是内存态,turn 结束丢(笔记 38 优化点 1 要补的)

### 级 ④:保留区 tool 消息裁剪(中,兜底)

**位置**:`manageContextWindow` → `trimToolResultsToBudget`(observe.go:221)

**白话**:Compaction 的残局兜底。**注意作用域不是"单轮",是保留区内所有 tool 消息**(Compaction 之后保留区全是 recent,没有新老可挑)。所有 tool 消息合计超过 `窗口/5`(下限 8K 上限 32K)时:先全没收发收据(占位符),再从最新往最旧用剩余预算赎回完整原文,塞不下的给头尾预览(头 1/4 尾 3/4,二分找最大可塞长度)。

**三条出场路径**(不是固定在 Compaction 之后):
1. Compaction 跑完还超阈值
2. Compaction 没东西可压(ErrNothingToCompact)或省不够 5%
3. overflow 强压(forceCompaction)失败

**三条铁律**:
- 只动 tool 消息 Content,不动 assistant 的 ToolCalls(保 OpenAI 配对)
- 返回拷贝不改原件(SSE / 诊断 / 持久化还在用原始 ToolResult)
- 所有 tool 结果都是候选(不分轮次)

## 三、执行顺序 vs 粒度顺序

```
进 loop 前(每 turn 一次):
  ①CompactToolOutputForHistory   ← 读 DB 时按类型裁
  ②redactHistoryKBResults        ← 装配时强制涂黑 KB 结果
       ↓
进 loop(每轮开头):
  ③闸1 Compaction                ← 超阈值,摘要替换,留尾部 2 万原文
       ↓ 还超 / 没东西可压 / overflow 强压失败
  ④闸2 trimToolResults           ← 兜底,所有 tool 消息合计超窗口/5
```

粒度排序是 ①②(细)→ ④(中)→ ③(粗),执行排序是 ①②③④。
④粒度居中但排在最后,因为它是兜底——只有 ③ 搞不定的残局才出场。

## 四、四级对照表(一图看完)

| 维度 | ①单工具压缩 | ②KB 涂黑 | ④tool 裁剪(兜底) | ③全量摘要 |
|---|---|---|---|---|
| **粒度** | 最细 | 细 | 中 | 最粗 |
| **执行位置** | 读 DB 时 | 装配时 | loop 内 | loop 内 |
| **作用域** | 单个工具结果 | 历史 turn 的 KB 工具结果 | 保留区所有 tool 消息 | 切线以前全部历史 |
| **手段** | 按类型裁成元信息 | 换固定占位符 | 占位符 + 赎回 + 头尾预览 | LLM 生成结构化摘要 |
| **动机** | 省 token | 防陈旧 | 省 token | 省 token |
| **调 LLM 吗** | 否 | 否 | 否 | **是**(唯一花钱的一级) |
| **信息可恢复吗** | 否(可重跑工具) | 否(就是要重新检索) | 否(可重跑工具) | 否(摘要接管) |
| **触发条件** | 每次读历史必做 | 每次装配必做(可配置关) | tool 合计 > 窗口/5 | 估算 > 窗口-16K |
| **跨 turn 持久吗** | 否(读时压) | 否(装配时涂) | 否(loop 内) | **否**(内存态,优化点 1) |

**只有 ③ 调 LLM**——四级里唯一花钱的一级,所以也是唯一需要"验收(5%)"和"降级(rawArchive)"保护的一级。其余三级都是纯规则,零成本瞬间完成。

---

## 五、为什么是这个阶梯形状(设计观察)

1. **便宜的先上,贵的最后上**:①②④纯规则零成本,每次都做;③要花 LLM 钱,所以设阈值 + 验收 + 降级三重保险,尽量少触发
2. **作用域层层嵌套不重叠**:①管单条,②管单类(KB 工具)的跨 turn 历史,④管保留区单角色(tool 消息),③管全部——各自的盲区正好被下一级补上
3. **每级都有"可恢复"出口**:①④裁掉的内容可以重跑工具拿回来,②涂黑就是逼你重新检索,③摘要接管但保了关键事实(Critical Context 栏)——丢信息不丢"怎么找回信息"
4. **唯一没持久化的是 ③**:①②在读取路径每次重算(幂等,无所谓),③的成果(摘要)却是花钱买的一次性消费——这正是笔记 38 优化点 1 的动机
