## 一、commit 22489ba6 · 提升 prompt cache 命中率(6 个改动)

### 0. 背景:prompt cache 是怎么工作的

provider(OpenAI / Anthropic / Aliyun)按 **prefix 字节匹配**:
- 请求的 prefix 跟上次一样 → 命中,用缓存的 KV,省 token
- prefix 变了一个字 → 全部 miss,重新算

请求分三段:
```
[stable prefix 段]  system + tools(理论上不变)
[对话历史段]        多轮对话累积
[当前轮段]          这次的 user + tool 结果
```

**命中率的命门在 stable prefix**——只要前缀一动,后面全 miss。

### 1. current_time 从 RFC3339 降到日期级

**旧**:`time.Now().Format(time.RFC3339)` → `2026-09-01T15:30:45+08:00`
**新**:`time.Now().Format("2006-01-02")` → `2026-09-01`

**为啥**:RFC3339 精确到秒,每秒都变,system prompt 每次都不一样,cache 全 miss。
降到日期级,一天内 system prompt 不变,cache 能命中一整天。

**位置**:
- `internal/agent/observe.go` manageContextWindow 里塞 current_time
- `internal/types/placeholder.go` 占位符定义
- `config/prompt_templates/system_prompt.yaml` 模板里 `{{current_time}}`

### 2. 不在对话中途改 system prompt(appendToolResults 挪到末尾)

**旧**:`appendToolResults` 一开头就改 system prompt(塞图片要求 / 检索说明),
中途改 system = 改 stable prefix = cache 全 miss。

**新**:
- `appendToolResults` 不再开头改 system,改成**在末尾追加 user 消息**
- `appendAgentRetrievedImageRequirement`(image_requirement.go)从"改 system"改成"追加 user 消息"
- 检索说明挪进 system_prompt.yaml 模板(静态)

**效果**:对话中途 system prompt 不动,cache 稳定命中。

### 3. 主动给 provider 发 cache 标记(prompt_cache.go 新增 230 行)

**旧**:靠 provider 自己识别 prefix(不一定识别得准,而且不同 provider 机制不同)。
**新**:`prompt_cache.go` 主动按 provider 分发标记:

| Provider | 标记方式 |
|---|---|
| OpenAI / Azure / OpenRouter | `prompt_cache_key`(64 字符截断)+ session_affinity HTTP 头 |
| Anthropic / Aliyun | `cache_control` 断点(在 system 消息 + 最后一条对话 + 最后一个 tool 上打) |

**关键函数**:
- `promptCachePolicyFor` 按 provider 分发策略
- `applyPromptCacheToJSONBody` 注入标记到请求 JSON
- `applyCacheControlBreakpoints` 给 Anthropic 打 cache_control 断点
- `attachPromptCacheHeaders` 设 session_id / x-client-request-id / x-session-affinity HTTP 头
- `clampPromptCacheKey` 限制 64 字符(OpenAI 限制)

**CacheRetention 三档**:None / Short / Long(控制缓存保留时长)

### 4. 摘要本身禁缓存(CacheRetention: None)

**为啥**:摘要是中间态,下次对话用不上,缓存它浪费钱。
Compactor 里 `CacheRetention: None` 显式声明。

### 5. 日志加 cache 命中率(engine.go:654)

**旧**:日志只有 token 数。
**新**:加 `cache_hit_rate` / `cache_read` / `cache_write` / `cache_status`。

**PromptCacheHitRate()** 方法(placeholder.go):
```go
hitRate = CacheReadTokens / PromptTokens * 100
```

### 6. current_time 前端挪走

旧版前端会显示精确时间,新版改成日期级,跟后端对齐。

| `internal/agent/think.go:260` + `finalize.go:108` | 加 PromptCacheKey: sessionID |

## 二、commit 4c0d42c4 · 上下文管理重构(11 个变化)

### 1. 目录重命名:`memory/` → `compaction/`

**旧**:`internal/agent/memory/`(叫"memory"但其实是压缩,名不副实)
**新**:`internal/agent/compaction/`(名副其实)

顺便清理:旧的 `internal/agent/token/compress.go` 删了(合并进 compaction)。

### 2. 4 道闸 → 2 道闸

**旧 4 道闸**(笔记 27):
1. trim(简单截断)
2. redact(涂黑 KB 工具结果)
3. Consolidator(整理对话)
4. CompressContext(压缩)

**新 2 道闸**(manageContextWindow 重写):
1. **Compaction**(主):结构化摘要 + 增量更新 + overflow 恢复
2. **trimToolResults**(兜底):工具结果超限就裁剪

**白话**:旧的 4 道闸是"层层过滤",新的 2 道闸是"一把摘要 + 一把兜底"。

### 3. 阈值从相对值改成绝对值

**旧**:`Threshold = MaxContextTokens * 0.8`(相对百分比)
**新**:
```go
DefaultReserveTokens   = 16384  // 预留 16K
DefaultKeepRecentTokens = 20000  // 保留最近 20K
Threshold = MaxContextTokens - ReserveTokens  // 触发摘要的阈值
KeepRecentTokens 上限 = usable / 4
```

**为啥**:绝对值更直观,不同模型 context window 大小不一样,绝对值跨模型可调。

### 4. 结构化摘要模板(8 章节)

**旧**:自由文本摘要,模型想写啥写啥,容易漏关键信息。
**新**:`compaction/prompts.go` 定义 8 章节模板:
1. **Goal** —— 用户要干啥
2. **Constraints** —— 约束条件
3. **Progress** —— 已完成
4. **In Progress** —— 进行中
5. **Blocked** —— 卡住的地方
6. **Key Decisions** —— 关键决策
7. **Next Steps** —— 下一步
8. **Critical Context** —— 必须记住的上下文

**为啥**:结构化模板保证关键信息不丢,模型有明确清单要填。

### 5. 增量更新摘要(updateSummarizationInstructions)

**旧**:每次摘要都从头重写(initialSummarizationInstructions)。
**新**:
- 第一次:用 `initialSummarizationInstructions`(从头写)
- 后续:用 `updateSummarizationInstructions`(在旧摘要基础上增量更新)

**白话**:"CONDENSE as you go"——摘要本身也走增量更新,不是每次推倒重来。

### 6. 摘要作为 user 消息而非 system 消息

**旧**:摘要塞进 system prompt(改 stable prefix → cache miss)。
**新**:摘要作为 **user 消息**追加(不动 system,cache 稳定)。

**位置**:`compaction/prepare.go` Preparation 结构体,summaryPrefix / summarySuffix。

**为啥**:跟 commit 22489ba6 的 cache 命中率优化一脉相承——system 不能动。

### 7. 切点算法 FindCutPoint 重写

**旧**:切点参考当前轮,容易把相关上下文切掉。
**新**:`compaction/cutpoint.go`:
- `FindCutPoint` **不参考当前轮**(只看历史)
- `isCutPointMessage` 排除 tool 结果(tool 结果不独立成切点)
- `isTurnStartMessage` 识别 turn 边界
- `historyStart` 找历史起点
- **允许切 turn 内部**(不光在 turn 边界切)

**白话**:旧的怕切到当前轮,新的明确"历史归历史、当前归当前",切点只管历史段。

### 8. 防无效摘要循环(minFreedFraction = 5%)

**问题**:摘要完发现只省了一点点 token,下一轮又触发摘要,死循环。
**新**:
```go
minFreedFraction = 20  // 1/20 = 5%
```
摘要完检查释放的 token 比例,**低于 5% 不认账**,继续往上切更多。

**白话**:摘要至少要省 5% 才算数,不然白干。

### 9. overflow 恢复(forceCompaction)

**问题**:provider 报 context overflow 错误,Agent 直接挂。
**新**:`compaction/overflow.go`:
- `IsOverflowError` 识别 20+ 种 provider 溢出错误(正则匹配)
- 捕到 overflow → `forceCompaction` 强制摘要 + 重试

**白话**:以前超限就崩,现在超限就强行压缩再试一次。

### 10. max_iterations 从有限改成 -1(无限)

**旧**:ReAct 循环有最大迭代次数限制。
**新**:改成 -1(无限),靠 overflow 恢复 + 摘要兜底,不靠硬上限。

**白话**:以前怕死循环限制次数,现在有 overflow 恢复就不怕了,放开跑。

### 11. 模型声明 context_window

**旧**:硬编码模型上下文窗口大小。
**新**:模型自己声明 context_window,Agent 读模型的声明。

**为啥**:新模型 context window 大小不一(4K / 32K / 128K / 200K),硬编码跟不上。

| `internal/agent/compaction/cutpoint.go` | 新增,FindCutPoint |

## 三、对照之前讨论的优化方向,看落地情况

笔记 27 之后讨论过几个优化方向,看新版怎么落地的:

| 优化方向 | 旧版做法 | 新版做法 | 落地情况 |
|---|---|---|---|
| **cache 命中率** | 靠 provider 自己识别 | 主动发标记 + system 不动 + current_time 降级 | ✅ 落地 |
| **压缩信息丢失** | 自由摘要,容易漏 | 8 章节结构化模板 | ✅ 落地 |
| **摘要推倒重来** | 每次从头写 | 增量更新(updateSummarizationInstructions) | ✅ 落地 |
| **overflow 崩溃** | 直接挂 | forceCompaction + 重试 | ✅ 落地 |
| **死循环防护** | max_iterations 硬上限 | minFreedFraction 5% 防无效摘要 + overflow 恢复 | ✅ 落地 |
| **阈值跨模型** | 相对百分比 | 绝对值 + 模型声明 context_window | ✅ 落地 |
| **涂黑 KB 结果** | redactHistoryKBResults 单独一道闸 | 合进 Compaction(serialize.go 里 toolResultMaxChars=2000) | ✅ 合并 |
| **简单截断 trim** | 单独一道闸 | trimToolResults 兜底(只裁工具结果) | ✅ 降级为兜底 |

**结论**:讨论过的优化方向基本都落地了,而且比预想更彻底——4 道闸直接砍成 2 道闸。

## 四、新版 2 道闸骨架(给后续看代码用)

```
manageContextWindow(observe.go)
  │
  ├─ 闸 1:Compaction(compaction/compactor.go)
  │    ├─ 触发条件:historyTokens > Threshold(MaxContext - 16384)
  │    ├─ FindCutPoint 找切点(不参考当前轮,允许切 turn 内部)
  │    ├─ serializeConversation 序列化要摘要的部分
  │    │    └─ toolResultMaxChars=2000, textMaxChars=4000, toolArgsMaxChars=400
  │    ├─ 选 initial / update 指令(第一次 vs 后续)
  │    ├─ LLM 生成 8 章节结构化摘要
  │    ├─ 摘要作为 user 消息追加(不动 system)
  │    ├─ minFreedFraction 5% 检查(低于不认账,继续切更多)
  │    └─ CacheRetention: None(摘要本身禁缓存)
  │
  └─ 闸 2:trimToolResults(兜底)
       ├─ minToolResultTokens = 8 * 1024
       ├─ maxToolResultTokens = 32 * 1024
       └─ toolResultTokenFraction = 5(1/5)
            工具结果超 max 就裁到 min,保证留最近的内容
```

**overflow 恢复路径**(独立于 2 道闸):
```
LLM 调用返回 overflow 错误
  → IsOverflowError 识别(20+ 正则)
  → forceCompaction 强制摘要
  → 重试 LLM 调用
```
