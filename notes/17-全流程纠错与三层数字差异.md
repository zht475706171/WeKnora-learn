# 17 · 全流程纠错 + 三层为什么用不同数字(256/128/无)

> 用户讲了一遍从体检到 T3 的全流程,我挑了 5 个错。然后追问"为啥不都用 256",解释三层用不同数字的原因。

---

## 一、用户讲的全流程(简版)

1. **体检**:正则扫标题/占位符,判断用哪个 tier
2. **T1**:扫到标题 → 从最高级往低级找 ≥3 个的层级切 → ContextHeader 记面包屑 → 向量化时拼接 → 大块调 T3,小块合并,失败降级 T3
3. **T2**:8 个正则切 → 超大 unit 委托 T3 → 装箱 → 失败降级 T3
4. **T3**:`\n\n > \n > 。` 递归切 unit → mergeUnits 贪心合并 → overlap 80 字
5. **保护机制**:代码/表格/LaTeX/链接/图片不被切,7500 硬上限

---

## 二、挑出的 5 个错

### 错误 1:T1 切割条件 ">" 应该是 ">="

- 用户说:某一级标题数量 **> 3** 个才切
- 实际:`>= 3`

### 错误 2:T2 装箱封口条件说反了

- 用户说:"装箱后长度 < 512/4 时继续装,装完下个 unit 判断成立则封口"
- 实际:`minChunkSize = chunkSize/4`(最小 50)是**防过早封口的下限**
- 封口**双条件**:
  1. `accumulated > 512`(加了下个会超)
  2. `curEnd - chunkStart >= 128`(当前已攒到 128)
- **两个同时成立才封口**

### 错误 3:T1 合并 target 说反了

- 用户说:"累计 < 512/2 就继续合,直到 > 512/2"
- 实际 `coalesceTinyChunks`:
  - `target = chunkSize/2 = 256`
  - 合并条件:`curLen < target && curLen+nextLen <= chunkSize`
  - 意思:**不到 256 才合,合到 ≥ 256 或加下个会爆 512 停**
  - 不是"合到 > 256",是"不到 256 才继续合"

### 错误 4:T2 "没有 overlap" 错

- 用户说:T2 没有 overlap
- 实际 `heuristic_splitter.go:98`:
  ```go
  chunkStart = applyOverlapAligned(runes, curEnd, cfg.ChunkOverlap, bounds)
  ```
- T2 **有 overlap**,默认 80,对齐到语义边界

### 错误 5:保护机制"不受递归影响"说法不准

- 用户说:保护机制不受递归调用影响
- 实际:**保护区间每次切分实时重算**,T3 递归进下层时是在**当前 unit 范围内**重新扫保护区间,不是用全文的
- 准确说法:"保护机制在每层都生效,但每次用的是当前文本范围的 span"

## 三、T2 封口双条件的细节(容易绕)

```go
if accumulated > cfg.ChunkSize && curEnd-chunkStart >= minChunkSize {
    // 封口
}
```

**关键**:两个量是**不同时刻**的:
- `accumulated = nextEnd - chunkStart` = **加了下个 block 之后**的总长度
- `curEnd - chunkStart` = **还没加下个**的当前长度

### 例 1:正常封口

```
当前 300 字,下个 250 字
accumulated = 550 > 512 ✓
curEnd - chunkStart = 300 >= 128 ✓
→ 封口!当前 300 字封掉
```

### 例 2:防过早封口

```
当前 80 字,下个 450 字
accumulated = 530 > 512 ✓
curEnd - chunkStart = 80 < 128 ✗
→ 不封!继续装 → chunk = 530(略超,可接受)
```

**为什么宁可超 512 也不要 80 字碎 chunk**:80 字碎 chunk 检索时命中率低,530 字虽然略超但语义完整。**防碎优先于严格不超**。

## 四、三层 chunk 大小保证(准确版)

| 层 | 上限 | 下限 | 机制 |
|----|------|------|------|
| T1 | section > 512 委托 T3,最终 ≤ 512 | target 256,小 section 合并 | coalesceTinyChunks(< 256 才合) |
| T2 | **可能略超 512**(防碎优先) | 封口下限 128(不到不让封) | minChunkSize 防过早封口 |
| T3 | 正常 ≤ 512 | **无下限保证**,最后 chunk 可能很小 | mergeUnits 装满 + overlap 80 + parent 兜底 |

### 几个关键点

- **T1 的 256 = ChunkSize/2**:**合并目标**(小 section 往大合)
- **T2 的 128 = ChunkSize/4**:**封口下限**(不到不让封,不是"合到 128")
- **T3 没数字下限**:mergeUnits 是**装满 512**逻辑,不是"装到 256";最后一个 chunk 是"剩多少是多少"

## 五、为啥不都用 256?(核心问题)

### 角度 1:三层的"敌人"不一样

| 层 | 主要敌人 | 数字的作用 |
|----|---------|-----------|
| T1 | 切碎标题结构 | 256 = **合并目标**(小 section 往大合) |
| T2 | 切太早(刚切一个 block 就封口) | 128 = **封口下限**(不到不让封) |
| T3 | 切到句子级还合不回(最后碎一地) | 无(靠 overlap + parent 兜) |

**T1 的敌人是"切碎标题结构"**:标题切出来 section 80 字,不合语义断裂;合到 256 刚好装下标题+正文。**256 = 语义完整的最小单位**。

**T2 的敌人是"过早封口"**:8 正则找到的 block 大小不均(30 字到 450 字)。80 字就封口会一堆碎 chunk。**128 = 宁可超一点也别碎**的阈值。

**T3 的敌人是"最后一块碎"**:mergeUnits 装满 512 才封,最后一个 chunk "剩多少是多少",没法控制。**干脆不设数字下限**,靠 overlap 80 + parent 兜底。

### 角度 2:数字大小反映"容忍碎的程度"

```
T1: 256   ← 最严格,标题语义必须完整
T2: 128   ← 中等,宁可超也不要碎
T3: 无    ← 最宽松,碎就碎,有 overlap 和 parent 兜
```

### 角度 3:数字来源不同,不是拍脑袋

- **T1 的 256 = ChunkSize/2**:合并目标"装到一半"
- **T2 的 128 = ChunkSize/4**(最小 50):封口下限"装到 1/4 才让封"
- **T3 没有**:mergeUnits 贪心装满逻辑

**256 和 128 都是 ChunkSize 的分数,但作用不同**:一个是"合并目标",一个是"封口下限"。**作用不同,数字自然不同**。

## 六、反过来想:都用 256 会咋样

### T2 用 256 会咋样

封口下限变成 256,意思是"不到 256 不让封":

```
当前 200,下个 320,合计 520 > 512
当前 200 ≥ 128 但 < 256
用 128:封口 → 当前 200 一个 chunk,下个 320 一个 chunk ✓
用 256:不封,继续装 → chunk = 520(略超),本来 200 可以独立的,现在被迫超 512
```

**T2 用 256 会让 chunk 经常超 512**,128 是"够一段意义就让你封"的平衡点。

### T3 用 256 会咋样

mergeUnits 装到 256 就封口?那 chunk 都 256~512,**比 512 多一倍的 chunk 数量**,存储和检索成本翻倍。

**T3 的设计就是"装满 512"**,不是"装到 256"。

---

## 七、一句话总结

**三层用不同数字,是因为三层的"敌人"和"手段"不同**:

- **T1 用 256 当合并目标**(小 section 合到 256,语义完整)
- **T2 用 128 当封口下限**(不到 128 不让封,防过早封口)
- **T3 不设下限**(mergeUnits 装满 512,靠 overlap + parent 兜最后一块)

**统一 256 会让 T2 经常超 512、T3 chunk 数翻倍**,反而更差。**好记不等于好用**,数字是**作用不同**,不是"随便定的"。

---

## 八、你应该带走的 4 件事

1. **T2 的 128 是"封口下限",不是"合并目标"**:作用是"不到 128 不让封",结果是**可能略超 512**,不是"保证 < 512"。

2. **T3 的 mergeUnits 是装满逻辑,不是装到 256**:正常 chunk 接近 512,**最后一个 chunk 可能很小**(没下限保证)。T3 没有 coalesce 后处理。

3. **T1 的 256 是合并目标**(小 chunk 合到 256),**T2 的 128 是封口下限**(不到不让封),**T3 没数字下限**——三层都用数字,但**作用完全不同**,别混。

4. **统一 256 会更差**:T2 会经常超 512(本可独立的小 chunk 被迫合大),T3 chunk 数翻倍(装到 256 就封而不是装满 512)。数字不同是因为**敌人不同**:T1 防碎标题、T2 防过早封口、T3 防最后一块碎(靠 overlap + parent 兜)。
