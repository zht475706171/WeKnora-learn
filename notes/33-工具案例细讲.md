# 笔记 33 · 工具案例细讲(definition / content / execute 三层)

> 接笔记 32(工具注册表)。笔记 32 讲 `ToolRegistry.ExecuteTool` 7 步分发的总机制,
> 本篇挑 3 个有代表性的工具,从"定义 / 内容 / 执行"三层展开细讲,看具体工具长啥样、怎么干活。
>
> 风格延续:专业术语 + 白话解释双轨。

---

## 一句话总结

**每个工具由三层组成**:
- **定义(Definition)**:`BaseTool{name, description, schema}` 静态字段,给模型看的"名片"
- **内容(Content)**:`Tool` 结构体 + 字段,装着干活需要的家伙(数据库连接 / 模型 / 缓存)
- **执行(Execute)**:`Execute(ctx, args) (*ToolResult, error)` 方法,真正干活的流程

**挑 3 个典型案例**覆盖三大类工具:
1. **`knowledge_search`(语义搜索)**——外部检索型,最复杂,内部跑完整检索 pipeline
2. **`thinking`(深度思考 / SequentialThinking)**——思维辅助型,纯内存,不调外部服务
3. **`todo_write`(制定计划)**——状态追踪型,最简单,几乎只做格式化

---

## 一、每个工具的三层结构

| 层 | 内容 | 白话 |
|---|---|---|
| **定义(Definition)** | `BaseTool{name, description, schema}` 静态字段 | 工具的"名片",给模型看,告诉模型"我叫啥、干啥、要什么参数" |
| **内容(Content)** | `Tool` 结构体 + 字段(依赖的服务、配置、状态) | 工具的"身体",装着干活需要的所有东西 |
| **执行(Execute)** | `Execute(ctx, args) (*ToolResult, error)` 方法 | 工具的"动作",拿到参数后真正干活 |

**白话**:每个工具都是"名片 + 身体 + 动作"三件套。名片给模型看(要不要用、怎么用),身体装家伙(数据库连接、模型),动作是真正干活。

## 二、案例 1:`knowledge_search`(语义搜索)——外部检索型

### 2.1 定义(Definition)

`knowledgeSearchTool`(knowledge_search.go:22)是个 `BaseTool` 静态变量:

```go
var knowledgeSearchTool = BaseTool{
    name: ToolKnowledgeSearch,  // "knowledge_search"
    description: `Semantic/vector search tool for retrieving knowledge by meaning, intent, and conceptual relevance.
    
    ## Purpose
    - conceptual explanations
    - topic overviews
    - reasoning-based information needs
    
    ## What the Tool Does NOT Do
    - Does NOT perform exact keyword matching
    - Should NOT receive long raw text or user messages as queries
    
    ## Parameters
    - queries (required): 1–5 semantic questions or conceptual statements.
    - knowledge_base_ids (optional): limit the search scope.
    
    Each chunk has a short cN source ID and belongs to a dN document ID.`,
    schema: json.RawMessage(`{
      "type": "object",
      "properties": {
        "queries": {
          "type": "array",
          "description": "REQUIRED: 1-5 semantic questions/topics",
          "items": {"type": "string"},
          "minItems": 1, "maxItems": 5
        },
        "knowledge_base_ids": {
          "type": "array",
          "description": "Optional: bound knowledge-base IDs (the short bN values)",
          "items": {"type": "string"},
          "maxItems": 10
        }
      },
      "required": ["queries"]
    }`),
}
```

**三个字段**:
- **`name`**:工具名 `"knowledge_search"`,注册表的 key
- **`description`**:给模型看的说明,告诉模型"这个工具干啥、什么时候用、什么时候不用、参数怎么填"。特意写了 **What the Tool Does NOT Do**(不干啥),防模型用错(比如拿关键词查询用这个工具,该用 `grep_chunks`)
- **`schema`**:JSON Schema 参数定义,给 OpenAI function calling 用,声明 `queries`(必填,1-5 个字符串)和 `knowledge_base_ids`(可选,最多 10 个)

**白话名片**:"我叫 `knowledge_search`,用向量检索找语义相似的内容(不是关键词匹配),你要给我 1-5 个短问题,我返回带 cN/dN ID 的 chunk 列表。"

### 2.2 内容(Content)

```go
type KnowledgeSearchTool struct {
    BaseTool                                              // 嵌入底座(提供 Name/Description/Parameters)
    knowledgeBaseService interfaces.KnowledgeBaseService  // KB 服务(检索入口)
    knowledgeService     interfaces.KnowledgeService      // Knowledge 服务
    chunkService         interfaces.ChunkService          // Chunk 服务(查 chunk 详情)
    searchTargets        types.SearchTargets              // 预算好的检索范围
    rerankModel          rerank.Reranker                  // rerank 模型(精排)
    chatModel            chat.Chat                        // LLM(rerank fallback 用)
    config               *config.Config                   // 全局配置(topK / 阈值)
    seenMu               sync.Mutex                       // 保护 seenChunks
    seenChunks           map[string]bool                  // 这个 session 已经返回过的 chunk
}
```

**关键字段**:
- `searchTargets`:预先算好的检索范围(哪些 KB、哪些 tag),工具不每次算,执行时只过滤
- `rerankModel` + `chatModel`:双 rerank 策略,优先用专用 rerank 模型,失败 fallback 用 LLM 打分
- `seenChunks`:**这个 session 已经返回过的 chunk ID 集合**,防重复返回(下次遇到同一个 chunk,只给元数据不给内容,省 token)

**白话身体**:装着 KB 服务(检索)、chunk 服务(查详情)、rerank 模型(精排)、LLM(rerank 备胎)、还有个"已见 chunk"缓存(防重复返回浪费 token)。

### 2.3 执行(Execute)

`Execute`(knowledge_search.go:162)是工具最核心的方法,大概 10 步:

```
Step 1:  解析参数(queries + knowledge_base_ids)
Step 2:  校验 knowledge_base_ids 在 searchTargets 里(授权层)
Step 3:  过滤 searchTargets(只保留 vector/keyword KB,跳过 wiki/graph-only)
Step 4:  并发检索(concurrentSearchByTargets)
         - 按 embedding model 分组(同模型的 KB 共用一次 query embedding)
         - 每个 (model, query) pair 算一次 embedding
         - 调 HybridSearch(向量 + 关键词 + RRF 融成,笔记 24 讲过)
Step 5:  去重(deduplicateResults)
         - 多 key 去重(chunk ID / parent chunk ID / kb+index)
         - 内容签名去重(防近重复)
Step 6:  Rerank(rerankResults)
         - 优先 rerankModel(cross-encoder 精排)
         - 失败 fallback chatModel(LLM 打分,15 个一批,温度 0.1)
         - 阈值过滤(< 0.3 丢,但保 top 1 防全军覆没)
Step 7:  MMR(applyMMR,Maximal Marginal Relevance)
         - lambda=0.7,平衡相关性和多样性
         - 防返回一堆内容几乎一样的 chunk
Step 8:  最终去重 + 排序(按 score 降序)
Step 9:  富化图片信息(EnrichSearchResultsImageInfo)
Step 10: 格式化输出(formatOutput)
         - XML 格式:<search_results><chunk rank="1" chunk_id="c1" ...><content>...</content></chunk>...
         - 已经见过的 chunk 标 already_seen="true",只给元数据不给内容(省 token)
         - 末尾加 <retrieval_statistics> 每个 doc 的覆盖率
```

### 2.4 关键设计

**① 并发检索按 embedding model 分组**:
不同 KB 可能用不同 embedding model(比如 KB A 用 OpenAI,B 用 BGE)。同模型的 KB 共用一次 query embedding(不算重复),不同模型各算一次。这是性能优化。

**② 双 rerank 策略**:
- 优先用专用 rerank 模型(cross-encoder,快且准)
- 失败 fallback 用 LLM 打分(慢但通用,15 个一批防 token 溢出)
- 温度 0.1(打分要稳定,不要创意)

**③ MMR 防冗余**:
返回的 chunk 如果内容高度相似(用 Jaccard 相似度衡量),MMR 会淘汰冗余的,保证多样性。
**白话**:防返回 5 个几乎一样的 chunk,浪费 context window。

**④ `seenChunks` 省 token**:
这个 session 已经返回过的 chunk,下次再检索到,只给元数据(标题/score/ID)不给内容,加 `already_seen="true"` 标记。
**白话**:模型已经在 context 里有这段内容了,再给一遍就是浪费 token,给个"你之前看过了"的提示就行。

**⑤ XML 格式输出**:
```xml
<search_results count="3">
  <query>腾讯的知识管理框架</query>
  <documents>
    <document knowledge_id="d1" knowledge_base_id="kb1" title="WeKnora 架构">
      <metadata>...</metadata>
    </document>
  </documents>
  <chunk rank="1" chunk_id="c1" chunk_index="0" knowledge_id="d1" knowledge_base_id="kb1" knowledge_title="WeKnora 架构" score="0.85" source_query="腾讯的知识管理框架">
    <match_snippet>... WeKnora 是腾讯开源的 ...</match_snippet>
    <content>WeKnora 是腾讯开源的知识管理框架...</content>
  </chunk>
  <chunk rank="2" chunk_id="c5" chunk_index="4" ... already_seen="true">
    <note>(content omitted, already returned in a previous knowledge_search call this session)</note>
  </chunk>
  <retrieval_statistics>
    <document_stat knowledge_id="d1" title="WeKnora 架构" total_chunks="20" retrieved="2" remaining="18" coverage="10.0%" />
  </retrieval_statistics>
</search_results>
```

**为什么 XML**:结构化,模型容易解析,而且 cN/dN/bN 这些短 ID 在 XML 属性里很容易被模型引用(笔记 32 讲过的"模型句柄")。

**⑥ retrieval_statistics 覆盖率提示**:
末尾告诉模型"这个文档总共有 20 个 chunk,你检索到 2 个,还剩 18 个,覆盖率 10%"。
**白话**:让模型知道"我看到的只是冰山一角",如果需要更多可以用 `list_knowledge_chunks` 翻完整文档。

### 2.5 整体流程

```
模型调 knowledge_search({"queries": ["WeKnora 是什么"], "knowledge_base_ids": ["kb1"]})
  ↓
解析参数 + 校验 KB 在范围
  ↓
过滤掉非 vector/keyword KB
  ↓
按 embedding model 分组,并发检索
  ↓ HybridSearch(向量 + 关键词 + RRF)
  ↓
去重(多 key + 内容签名)
  ↓
Rerank(专用模型 → LLM fallback,阈值 0.3)
  ↓
MMR(lambda=0.7,防冗余)
  ↓
最终去重 + 排序
  ↓
富化图片信息
  ↓
格式化输出(XML + seenChunks 省 token + 覆盖率统计)
  ↓
返回 ToolResult{Success: true, Output: "<search_results>...</search_results>", Data: {...}}
```

## 三、案例 2:`thinking`(深度思考)——思维辅助型

### 3.1 定义(Definition)

```go
var sequentialThinkingTool = BaseTool{
    name: ToolThinking,  // "thinking"
    description: `A detailed tool for dynamic and reflective problem-solving through thoughts.
    
    ## When to Use This Tool
    - Breaking down complex problems into steps
    - Planning and design with room for revision
    - Analysis that might need course correction
    
    ## Key Features
    - You can adjust total_thoughts up or down as you progress
    - You can question or revise previous thoughts
    - You can add more thoughts even after reaching what seemed to be the end
    
    **CRITICAL - User-Friendly Thinking**: Write your thoughts in natural, user-friendly language. NEVER mention tool names (like "grep_chunks", "knowledge_search", "web_search", etc.) in your thinking process.
    
    - **thought**: Your current thinking step
    - **next_thought_needed**: True if you need more thinking
    - **thought_number**: Current number in sequence
    - **total_thoughts**: Current estimate of thoughts needed
    - **is_revision**: A boolean indicating if this thought revises previous thinking
    - **revises_thought**: If is_revision is true, which thought number is being reconsidered
    - **branch_from_thought**: If branching, which thought number is the branching point
    - **branch_id**: Identifier for the current branch
    - **needs_more_thoughts**: If reaching end but realizing more thoughts needed`,
    schema: json.RawMessage(`{...}`),
}
```

**特点**:
- 这个工具**不调任何外部服务**,纯思维脚手架
- 参数全是"思考状态":thought / thought_number / total_thoughts / is_revision / branch_id 等
- description 里强调"用自然语言思考,不要提工具名"——防模型把思考写成"我要用 grep_chunks 然后 knowledge_search"(用户看着像机器日志,体验差)

**白话名片**:"我叫 `thinking`,是个反思性思考工具,你一步步想问题用我,可以改主意、可以分支、可以追加思考,但请用自然语言思考,别提工具名。"

### 3.2 内容(Content)

```go
type SequentialThinkingTool struct {
    BaseTool                                       // 底座
    thoughtHistory []SequentialThinkingInput       // 思考历史(这个 session 的所有思考)
    branches       map[string][]SequentialThinkingInput  // 分支(按 branch_id 索引)
}
```

**关键字段**:
- `thoughtHistory`:这个 session 所有思考的数组,工具自己维护(内存里)
- `branches`:分支思考,按 `branch_id` 索引

**白话身体**:就两个数组,一个记主线的所有思考,一个记分支思考。**没有外部依赖,不连数据库不连模型**。

### 3.3 执行(Execute)

```go
func (t *SequentialThinkingTool) Execute(ctx, args) (*types.ToolResult, error) {
    // Step 1: 解析参数
    var input SequentialThinkingInput
    if err := json.Unmarshal(args, &input); err != nil {...}
    
    // Step 2: 校验(thought 非空,thoughtNumber >= 1,totalThoughts >= 1)
    if err := t.validate(input); err != nil {...}
    
    // Step 3: 动态调整 totalThoughts(如果 thoughtNumber 超过 totalThoughts,就调大)
    if input.ThoughtNumber > input.TotalThoughts {
        input.TotalThoughts = input.ThoughtNumber
    }
    
    // Step 4: 记进 thoughtHistory
    t.thoughtHistory = append(t.thoughtHistory, input)
    
    // Step 5: 处理分支(如果是 branch,记进 branches map)
    if input.BranchFromThought != nil && input.BranchID != "" {
        if t.branches[input.BranchID] == nil {
            t.branches[input.BranchID] = make([]SequentialThinkingInput, 0)
        }
        t.branches[input.BranchID] = append(t.branches[input.BranchID], input)
    }
    
    // Step 6: 返回
    incomplete := input.NextThoughtNeeded || input.NeedsMoreThoughts || input.ThoughtNumber < input.TotalThoughts
    return &types.ToolResult{
        Success: true,
        Output:  "Thought process recorded" 或 "...unfinished steps remain, continue exploring",
        Data: map[string]interface{}{
            "thought_number":         input.ThoughtNumber,
            "total_thoughts":         input.TotalThoughts,
            "next_thought_needed":    input.NextThoughtNeeded,
            "branches":               branchKeys,
            "thought_history_length": len(t.thoughtHistory),
            "display_type":           "thinking",
            "thought":                input.Thought,
            "incomplete_steps":       incomplete,
        },
    }, nil
}
```

**白话动作**:
1. 解析参数
2. 校验(thought 不能空,编号不能小于 1)
3. 动态调整总数(如果当前编号超过预估总数,把总数调大)
4. 记进历史(append 到 `thoughtHistory`)
5. 处理分支(如果有 `branch_id`,记进 `branches` map)
6. 返回"已记录"+ 状态数据(编号/总数/是否还要继续/分支列表)

### 3.4 关键设计

**① 不调外部服务**:这个工具纯内存,不连数据库不连模型,执行超快(微秒级)。
**为什么这样**:思考是模型自己的事,工具只是"记一笔 + 提示还要不要继续",不需要外部资源。

**② 动态调整 totalThoughts**:模型一开始可能估"我要思考 5 步",结果想到第 7 步还没完,工具允许 `thought_number=7 > total_thoughts=5`,自动调大 totalThoughts 到 7。
**白话**:允许模型"改主意",不强制按预估步数走。

**③ 分支思考**:模型可以"从第 3 步分叉,走 branch_id=B1 的新思路",分支独立记。
**白话**:允许模型"试试别的路",不一条道走到黑。

**④ `incomplete_steps` 标志**:如果 `next_thought_needed=true` 或 `thought_number < total_thoughts`,返回"incomplete",提示模型"还有步没想完,继续"。

**⑤ 前端展示**:`display_type: "thinking"`,前端看到这个标记,把内容渲染成"AI 正在思考..."的折叠块,跟最终答案区分。

### 3.5 跟 `knowledge_search` 的对比

| 维度 | `knowledge_search` | `thinking` |
|---|---|---|
| 外部依赖 | KB 服务 / chunk 服务 / rerank / LLM | 无 |
| 执行耗时 | 秒级(检索 + rerank) | 微秒级(只 append 数组) |
| 输出 | XML 检索结果 | "已记录" + 状态数据 |
| 用途 | 找外部信息 | 组织模型自己的思考 |
| 超时 | 受工具 60s 超时约束 | 几乎不可能超时 |

**白话**:`knowledge_search` 是"出去找资料",`thinking` 是"自己想问题"。一个外向一个内向。

## 四、案例 3:`todo_write`(制定计划)——状态追踪型

### 4.1 定义(Definition)

```go
var todoWriteTool = BaseTool{
    name: ToolTodoWrite,  // "todo_write"
    description: `Use this tool to create and manage a structured task list for retrieval and research tasks.
    
    **CRITICAL - Focus on Retrieval Tasks Only**:
    - This tool is for tracking RETRIEVAL and RESEARCH tasks
    - DO NOT include summary or synthesis tasks - those are handled by the thinking tool
    
    ## When to Use This Tool
    1. Complex multi-step tasks - When a task requires 3 or more distinct steps
    2. Non-trivial and complex tasks
    3. User explicitly requests todo list
    4. User provides multiple tasks
    
    ## When NOT to Use This Tool
    1. Only a single, straightforward task
    2. The task is trivial
    3. The task is purely conversational
    
    ## Examples of When to Use
    <example>
    User: Compare WeKnora with other RAG frameworks...
    Assistant: I'll help you compare... Let me create a retrieval plan...
    *Creates a todo list with retrieval tasks: 1) Search KB for WeKnora, 2) web_search for LangChain, 3) web_search for LlamaIndex, 4) Retrieve comparison points*
    </example>
    
    ## Task States and Management
    1. **Task States**: pending / in_progress / completed
    2. **Task Management**: 
       - Only have ONE task in_progress at any time
       - Mark tasks complete IMMATELY after finishing
       - Remove tasks no longer relevant
    3. **Task Completion Requirements**:
       - ONLY mark completed when FULLY accomplished
       - Never mark completed if: Tests failing / Implementation partial / Errors unresolved`,
    schema: utils.GenerateSchema[TodoWriteInput](),
}
```

**特点**:
- description 里**反复强调**"只管检索任务,不管总结(总结归 thinking)"——防模型把"总结"也写进 todo
- 例子很具体(正面例子 + 反面例子),教模型什么时候用什么时候不用
- 状态管理规则清晰(pending / in_progress / completed,同时只能一个 in_progress)

**白话名片**:"我叫 `todo_write`,帮你管检索任务清单,只管'查什么',不管'怎么总结'(那是 thinking 的事)。3 步以上复杂任务才用我,简单任务别用。"

4. 返回

### 4.4 关键设计

**① 无状态**:工具不存历史,每次调用都从头来。模型每次调都传完整 todo 列表(更新某个 step 状态后,整个列表重新传)。
**白话**:工具是个"白板",模型每次把完整计划写上去,工具格式化展示,不记历史。

**② `display_type: "plan"`**:前端看到这个标记,渲染成"计划清单"UI(带勾选框、进度条),不是普通文本。

**③ 进度统计 + 提醒**:输出末尾自动算"总 3 个,完成 1 个,剩余 2 个",加粗提醒"剩余任务必须完成才能总结"。
**白话**:防模型半途而废,没查完就开始瞎总结。

**④ 跟 `thinking` 的分工**:
- `todo_write`:管"查什么"(检索任务)
- `thinking`:管"怎么综合"(总结分析)
- description 里特意写"DO NOT include summary tasks",防模型把"总结"也写进 todo

### 4.5 跟 `thinking` 的对比

| 维度 | `thinking` | `todo_write` |
|---|---|---|
| 有状态吗 | 有(thoughtHistory + branches) | 无(每次从头来) |
| 用途 | 组织思考过程 | 追踪检索任务 |
| 输出 | "已记录" + 思考状态 | 格式化计划清单 + 进度统计 |
| 前端展示 | `display_type: "thinking"`(折叠思考块) | `display_type: "plan"`(计划清单 UI) |
| 谁记历史 | 工具自己记(append) | 模型每次传完整列表 |

**白话**:`thinking` 有状态(工具记思考历史),`todo_write` 无状态(模型每次传完整计划)。一个内向有记性,一个外向没记性。

## 六、总结:工具的本质

泰哥,这三个案例串起来看,WeKnora 的工具其实是**三类角色**:

### 6.1 外部检索型(`knowledge_search` / `grep_chunks` / `database_query` / `web_search` 等)

- 连外部服务,干活(找资料 / 查 DB / 抓网页)
- 有状态(seenChunks 之类的去重缓存)
- 输出结构化数据(XML / JSON),带 cN/dN 短 ID 供模型引用
- 受 60s 超时约束
- **本质**:模型的"手脚",替模型去外部世界取信息

### 6.2 思维辅助型(`thinking`)

- 不连外部,纯内存
- 有状态(思考历史 + 分支)
- 输出"已记录" + 状态数据
- 微秒级,不可能超时
- **本质**:模型的"笔记本",帮模型把思考过程外化(写下来比闷头想更清楚)

### 6.3 状态追踪型(`todo_write`)

- 不连外部,纯格式化
- 无状态(模型每次传完整列表)
- 输出格式化计划 + 进度统计
- 微秒级
- **本质**:模型的"任务看板",帮模型管多步任务的进度,防半途而废

### 6.4 三个共同点

- 都实现 `types.Tool` 接口(4 方法:Name / Description / Parameters / Execute)
- 都嵌入 `BaseTool`(复用 Name/Description/Parameters)
- 都从 `ToolRegistry.ExecuteTool` 进来(笔记 32 的 7 步预处理)
- 都返回 `*types.ToolResult`(Success / Output / Data / Images)
- 失败都加 `toolErrorHint` 让模型换思路

**白话总结**:
- 工具的"定义"是给模型看的名片(名字 + 说明书 + 参数表)
- 工具的"内容"是装着干活需要的家伙(数据库连接 / 模型 / 缓存)
- 工具的"执行"是真正干活的流程(解析参数 → 干活 → 格式化结果)
