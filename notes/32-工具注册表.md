## 一句话总结

**`ToolRegistry` = 工具字典 + 输出预算管理员**(registry.go,注册表,管所有工具的注册和分发),
**`ExecuteTool` 7 步**(取工具 → CastParams 类型转换 → ValidateParams 校验 → 算输出预算 → `tool.Execute` 真正执行 → TruncateToolOutput 截断 → 三级日志),
**`types.Tool` 接口**定义所有工具的统一契约(Name / Description / Parameters / Execute),
**`BaseTool` 提供公共实现**(避免每个工具都写一遍 Name/Description/Parameters),
**注册时 first-wins 防劫持**(同名工具先注册的留,后注册的拒,防名字冲突被恶意工具劫持),
**输出预算 24000 字符**(DefaultMaxToolOutput,超过截断防 context window 中毒),
**KB 能力要求**(capabilities.go,工具跟 KB 的能力匹配关系,前端灰化 + 后端兜底)。

## 一、ToolRegistry 结构体(registry.go:19)

```go
type ToolRegistry struct {
    tools             map[string]types.Tool  ← 工具字典,key 是工具名
    maxToolOutputSize int                    ← 输出预算,0 用默认 24000
}
```

**白话**:`ToolRegistry`(工具注册表)就是个 map,key 是工具名(如 `"knowledge_search"`),value 是 `types.Tool` 接口的具体实现。额外管一个"输出预算"(默认 24000 字符)。

### 1.1 `types.Tool` 接口

```go
type Tool interface {
    Name() string                    ← 工具名
    Description() string             ← 工具描述(给模型看)
    Parameters() json.RawMessage     ← JSON Schema 参数定义
    Execute(ctx, args) (*ToolResult, error)  ← 执行
}
```

**白话**:所有工具都要实现这 4 个方法,这是统一契约。不管你是 `knowledge_search` 还是 `database_query` 还是 `shell_exec`,在注册表眼里都长这样。

### 1.2 `BaseTool` 公共实现

```go
type BaseTool struct {
    name        string
    description string
    schema      json.RawMessage
}
```

`BaseTool` 实现了 `Name() / Description() / Parameters()` 三个方法,
具体工具只要嵌入 `BaseTool` + 自己写 `Execute` 就行,不用重复写 3 个 getter。

**白话**:`BaseTool` 是"工具的底座",具体工具嵌进去就能用,只写 `Execute` 就行。

## 二、注册:`RegisterTool` first-wins 防劫持(registry.go:55)

```go
func (r *ToolRegistry) RegisterTool(tool types.Tool) {
    name := tool.Name()
    if _, exists := r.tools[name]; exists {
        logger.Warnf(context.Background(),
            "[ToolRegistry] Duplicate tool registration rejected: %s (first-wins policy)", name)
        return  ← 同名工具已存在,拒绝注册,保留先注册的
    }
    r.tools[name] = tool
}
```

**first-wins policy(先注册者胜)**:
- 同名工具先注册的留,后注册的拒
- **为什么**:防 name collision attack(名字冲突攻击)。如果恶意插件注册一个跟内置工具同名的工具,后注册者会被拒,不能劫持执行。

**白话**:注册时如果名字已经被占了,新来的被拒绝。防止恶意工具冒充内置工具(比如注册一个假的 `knowledge_search` 把检索结果偷走)。

参考安全公告 GHSA-67q9-58vj-32qx,这是真实漏洞的修复。

## 三、`GetFunctionDefinitions` 字节稳定(registry.go:92)

```go
func (r *ToolRegistry) GetFunctionDefinitions() []types.FunctionDefinition {
    names := make([]string, 0, len(r.tools))
    for name := range r.tools {
        names = append(names, name)
    }
    sort.Strings(names)  ← 排序!关键

    definitions := make([]types.FunctionDefinition, 0, len(names))
    for _, name := range names {  ← 按排序后的顺序遍历
        tool := r.tools[name]
        definitions = append(definitions, types.FunctionDefinition{
            Name:        tool.Name(),
            Description: tool.Description(),
            Parameters:  tool.Parameters(),
        })
    }
    return definitions
}
```

**为什么排序**:
- Go map 迭代顺序是**故意随机化**的(防用户依赖顺序)
- 工具定义发给 LLM 时,如果顺序乱,序列化后的 JSON 字节就不一样
- 有些 provider(Qwen explicit caching)的 prompt cache 是**字节级前缀匹配**——工具块顺序一变,cache 就 miss
- 排序后保证序列化字节跨请求一致,cache 才能命中

**白话**:工具列表要按名字排序,保证每次发给模型的 JSON 字节完全一样,这样 prompt cache 才能命中(省算省 token)。Go map 顺序是随机的,不排序就乱了。

## 四、`ExecuteTool` 7 步分发(registry.go:112)

这是 `runToolCall` Step 11 调的入口,工具执行的统一入口。

### 4.1 7 步流程

```
ExecuteTool(ctx, name, args) (*ToolResult, error):
  Step 1: PipelineInfo 日志(execute_start)
  Step 2: GetTool(name) → 找不到返回错误 + toolErrorHint
  Step 3: CastParams 类型转换(LLM 输出 "true" 转成 true)
  Step 4: ValidateParams 校验(必填/类型/枚举/范围/长度)→ 失败返回错误 + toolErrorHint
  Step 5: 算输出预算(maxOutput,支持工具自定义 OutputLimitChars)
  Step 6: tool.Execute(WithOutputBudget(ctx, maxOutput), args) 真正执行
  Step 7: TruncateToolOutput 截断(超预算截断)+ 三级日志
```

### 4.2 Step 2:GetTool 找不到的处理

```go
tool, err := r.GetTool(name)
if err != nil {
    return &types.ToolResult{
        Success: false,
        Error:   err.Error() + toolErrorHint,  ← 加错误提示
    }, err
}
```

`toolErrorHint` 是个常量(line 16):
```go
const toolErrorHint = "\n\n[Analyze the error above and try a different approach.]"
```

**白话**:工具找不到(模型幻觉一个不存在的工具名),返回错误,末尾加一句"分析上面的错误,换个思路"——告诉模型别再试这个不存在的工具了。

### 4.3 Step 3:CastParams 类型转换(registry.go:135, param_cast.go)

```go
args = CastParams(args, tool.Parameters())
```

**为什么需要**:LLM 有时输出错误类型:
- 该 `true` 输出 `"true"`(字符串而不是布尔)
- 该 `123` 输出 `"123"`(字符串而不是数字)
- 该数组输出单字符串

`CastParams` 按工具的 JSON Schema 做安全转换:
- 该 array 输出 string:尝试 JSON parse,失败就把单字符串包成 `[]string{s}`
- 该 boolean 输出 string:"true"/"false" 转 bool
- 该 number 输出 string:`strconv.ParseFloat`

**白话**:模型有时输出错类型("true" 而不是 true),CastParams 按工具的参数定义自动修正,避免无谓的执行失败。

### 4.4 Step 4:ValidateParams 校验(registry.go:139, param_validate.go)

```go
if validationErrs := ValidateParams(args, tool.Parameters()); len(validationErrs) > 0 {
    errMsg := FormatValidationErrors(validationErrs) + toolErrorHint
    return &types.ToolResult{
        Success: false,
        Error:   errMsg,
    }, nil  ← 注意返回 nil error(不是执行错误,是参数错)
}
```

**校验内容**:
- `required`:必填字段是否缺失
- `type`:JSON 类型是否匹配(string/number/integer/boolean/array/object)
- `enum`:值是否在允许集合
- `minimum`/`maximum`:数值范围
- `minLength`/`maxLength`:字符串长度

**关键设计**:校验失败返回 `nil` error(不是执行错误),`ToolResult.Success=false` + 错误信息。
**为什么这样**:执行错误和参数错误是两类。参数错误是模型问题,不该让 `runToolCall` 走重试逻辑(笔记 30 讲过,Act 不重试),应该直接把错误返回给模型让模型换思路。

**白话**:执行前先校验参数(必填/类型/枚举/范围/长度),不合规直接返回错误给模型,避免浪费一次工具执行 + LLM round。

### 4.5 Step 5:算输出预算(registry.go:153)

```go
maxOutput := r.getMaxToolOutput()  ← 默认 24000
if provider, ok := tool.(outputLimitProvider); ok {
    if toolLimit := provider.OutputLimitChars(args); toolLimit > maxOutput {
        maxOutput = toolLimit  ← 工具自定义预算可以放大,不能缩小
    }
}
```

**`outputLimitProvider` 接口**(registry.go:27):
```go
type outputLimitProvider interface {
    OutputLimitChars(args json.RawMessage) int
}
```

**白话**:默认预算 24000 字符。有些工具(比如 `data_analysis` 处理大数据)需要更大预算,可以实现 `OutputLimitChars` 方法自定义。**只能放大,不能缩小**(防工具自己设太小把输出截没了)。

**为什么这么设计**:有些工具的输出本身就是大批量数据(比如数据分析结果、图谱查询),统一 24000 会截断有用信息。让工具自己根据参数决定预算,更灵活。

### 4.6 Step 6:真正执行(registry.go:159)

```go
result, execErr := tool.Execute(WithOutputBudget(ctx, maxOutput), args)
```

`WithOutputBudget` 把预算通过 ctx 传给工具,工具可以用 `OutputBudget(ctx)` 拿到这个值,自己控制输出大小(避免截断损失结构)。

**白话**:调工具的 `Execute` 方法,把预算通过 ctx 传过去。工具可以主动按预算截断(比如检索结果只取 top K),也可以让注册表后续兜底截断。

### 4.7 Step 7:TruncateToolOutput 截断(registry.go:164)

```go
if result != nil && utf8.RuneCountInString(result.Output) > maxOutput {
    result.Output = TruncateToolOutput(result.Output, maxOutput)
}
```

**关键**:`utf8.RuneCountInString` 不是 `len()`(字节长度)。
- 中文字符是 3 字节,用 `len()` 衡量 24000 字节只能放 8000 个中文字
- 用 rune count 衡量 24000 runes 能放 24000 个中文字
- **白话**:用字符数(不是字节数)衡量,防中文输出被过度截断。

`TruncateToolOutput`(truncate.go:30):
```go
const DefaultMaxToolOutput = 24000
const truncationMarkerReserve = 200

func TruncateToolOutput(output string, maxChars int) string {
    if utf8.RuneCountInString(output) <= maxChars {
        return output
    }
    usable := maxChars - truncationMarkerReserve  ← 留 200 字给截断标记
    // 截到 usable 字符 + 加 "...(truncated)" 标记
}
```

**为什么留 200 字给标记**:截断标记本身要占字符(比如 `... [truncated to N chars]`),如果不预留,截断后总长可能超 maxChars。

### 4.8 三级日志 + toolErrorHint

```go
if execErr != nil {
    fields["error"] = execErr.Error()
    common.PipelineError(ctx, "AgentTool", "execute_done", fields)  ← 执行错误
} else if result != nil && !result.Success {
    if result.Error != "" {
        result.Error = result.Error + toolErrorHint  ← 工具返回失败,加错误提示
    }
    common.PipelineWarn(ctx, "AgentTool", "execute_done", fields)  ← 工具失败
} else {
    common.PipelineInfo(ctx, "AgentTool", "execute_done", fields)  ← 成功
}
```

**三级**:
- `PipelineError`:执行错误(execErr != nil,工具内部 panic 或 context 错)
- `PipelineWarn`:工具返回 Success=false(工具自己判断失败,比如检索没结果)
- `PipelineInfo`:成功

**`toolErrorHint` 在这里再加一次**:工具返回 `Success=false` 时,`result.Error` 末尾加 `toolErrorHint`,让模型看到"换思路"提示。

有些工具需要 KB(知识库)支持某种能力才能用:

### 6.2 `ToolRequirement` 结构

```go
type ToolRequirement struct {

    AllOf         []KBCapability  ← 必须全部满足
```

**两种语义**:

### 6.6 `ToolsConsumeFiles` 是否消费文件

```go
func ToolsConsumeFiles(allowedTools []string) bool {
    if len(allowedTools) == 0 {
        return true  ← 空列表视为可能消费(宽松)

        req, ok := ToolCapabilityRequirements[t]
        if !ok {
            return true  ← 未知工具(MCP 工具)视为可能消费(宽松)

        if req.ConsumesFiles {
            return true
        }
    }
    return false
}
```

**白话**:判断工具集是否消费用户文件。未知工具(MCP 工具)宽松视为消费,防意外隐藏文件选择器。

## 七、工具的授权层(scope_authorization.go)

**白话**:检索类工具内部调用前,先校验用户有没有权限访问这些 KB / chunk。比如用户 `@` 了 KB A,但 agent 配置里只允许 KB B,授权层会过滤掉 KB A。

## 八、关键设计要点

### 8.1 first-wins 防劫持

`RegisterTool` 同名先到先得,后到拒绝。防恶意工具冒充内置工具(参考 GHSA-67q9-58vj-32qx)。
**白话**:工具名先到先得,防恶意插件冒充内置工具偷数据。

### 8.2 GetFunctionDefinitions 排序保字节稳定

Go map 顺序随机,排序后保证序列化字节跨请求一致,字节级 prompt cache 才能命中(尤其 Qwen explicit caching)。
**白话**:工具列表按名字排序,每次发的 JSON 字节完全一样,prompt cache 才能命中。

### 8.3 CastParams + ValidateParams 双层预处理

执行前先转换类型 + 校验参数,避免无谓的工具执行失败 + LLM round 浪费。
**白话**:模型输出不百分百规范,先自动修正 + 校验,不合规直接返回错误,不浪费一次工具执行。

### 8.4 输出预算 rune count 不是 byte

`utf8.RuneCountInString` 衡量,中文 3 字节算 1 字符,防中文被过度截断。
**白话**:用字符数(不是字节数)衡量输出,防中文被截太多。

### 8.5 outputLimitProvider 工具自定义预算

工具可以实现 `OutputLimitChars(args)` 自定义预算,**只能放大不能缩小**(防工具自设太小)。
**白话**:有些工具需要更大输出(比如数据分析),可以自己设预算,但不能缩小默认值。

### 8.6 工具失败加 toolErrorHint

执行错误 / 工具返回失败 / 参数校验失败,都加 `toolErrorHint`(`[Analyze the error above and try a different approach.]`)提示模型换思路。
**白话**:工具失败时,错误信息末尾加一句"换思路",让模型下次试别的工具或参数。

### 8.7 KB 能力要求前后端同步

`ToolCapabilityRequirements` 跟前端 `tool-capabilities.ts` 必须同步,前端灰化 + 后端兜底。
**白话**:前端不让用户选不兼容的工具,后端再校验一次防绕过。

### 8.8 三类错误区分

| 错误类型 | 返回 | 处理 |
|---|---|---|
| 工具找不到 | `ToolResult{Success: false, Error: ...}` + `err` | `runToolCall` 记 error 日志 |
| 参数校验失败 | `ToolResult{Success: false, Error: ...}` + `nil err` | `runToolCall` 记 warn 日志 |
| 工具执行失败 | `ToolResult{Success: false, Error: ...}` + `nil err` 或 `err` | `runToolCall` 三级日志 |

**白话**:执行错误(execErr != nil)是工具内部 panic 或 ctx 错;参数错误和工具返回失败是模型问题,返回 nil err 让 `runToolCall` 不走错误路径,把错误给模型让模型换思路。

## 九、完整例子:模型调 `knowledge_search`

### 9.1 场景

模型返回 `tool_calls: [{function: {name: "knowledge_search", arguments: '{"query": "腾讯", "kb_id": "abc"}'}}]`。

### 9.2 流程

```
1. runToolCall Step 11:
   execCtx, toolCancel := context.WithTimeout(toolExecCtx, execTimeout=60s)
   result, err = e.toolRegistry.ExecuteTool(execCtx, "knowledge_search", args)
   toolCancel()

2. ToolRegistry.ExecuteTool:
   Step 1: PipelineInfo(execute_start, {tool: "knowledge_search", args: ...})
   Step 2: GetTool("knowledge_search") → 找到 KnowledgeSearchTool 实例
   Step 3: CastParams(args, schema)
           - schema 里 query 是 string,args 里 query 是 "腾讯"(string),匹配,不变
           - schema 里 kb_id 是 string,args 里 kb_id 是 "abc"(string),匹配,不变
           - 如果模型输出了 {"query": 123}(数字),CastParams 会转成 "123"
   Step 4: ValidateParams(args, schema)
           - required: ["query"] 都有,通过
           - type: query 是 string,通过
           - minLength/maxLength: query 长度 2,通过
   Step 5: maxOutput = 24000(默认)
           - KnowledgeSearchTool 如果实现了 OutputLimitChars(args):
             比如返回 50000,那 maxOutput = 50000(放大)
   Step 6: tool.Execute(WithOutputBudget(ctx, 24000), args)
           - KnowledgeSearchTool.Execute 内部:
             a. 解析参数(query, kb_id, ...)
             b. 授权校验(scope_authorization.go):kb_id 在 agent 允许的 KB 列表内?
             c. 调检索 pipeline(vector + keyword + rerank + merge,笔记 24 讲过)
             d. 按 OutputBudget(ctx) 截断结果(主动控制)
             e. 返回 ToolResult{Success: true, Output: "...", Data: ...}
   Step 7: TruncateToolOutput(result.Output, 24000)
           - 如果 result.Output 是 30000 字符,截断到 24000 - 200 = 23800 字符 + "... [truncated]" 标记
           - 如果是 20000 字符,不截断
   Step 8: 三级日志
           - execErr == nil,Success == true → PipelineInfo(execute_done, {success: true})
           - 如果 Success == false → PipelineWarn + 加 toolErrorHint 到 result.Error

3. 返回给 runToolCall:
   - ToolResult{Success: true, Output: "检索结果...", Data: ...}, nil
4. runToolCall 装 ToolCall{Result: result, ...} 推事件给前端
```

### 9.3 异常路径

**模型幻觉工具名**(比如 `knowledge_search_v2`):
- Step 2: GetTool 失败
- 返回 `ToolResult{Success: false, Error: "tool not found: knowledge_search_v2\n\n[Analyze the error above...]"}`
- 模型看到错误,下次换 `knowledge_search`

**参数校验失败**(比如 `query` 缺失):
- Step 4: ValidateParams 失败
- 返回 `ToolResult{Success: false, Error: "required parameter 'query' is missing\n\n[Analyze the error above...]"}`
- 模型看到错误,下次补上 `query`

**工具执行失败**(比如 KB 没授权):
- Step 6: tool.Execute 内部授权失败
- 返回 `ToolResult{Success: false, Error: "knowledge base not authorized: abc\n\n[Analyze the error above...]"}`
- 模型看到错误,下次换 KB 或换工具
