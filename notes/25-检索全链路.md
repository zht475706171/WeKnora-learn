# 25 · 检索全链路(query改写→双路并行检索→RRF融合→rerank两阶段→merge增厚→喂LLM)

> RAG 的"读"侧。之前笔记21/24摸过 resolveParentChunks,只是 merge 的一个子步骤。本篇讲完整检索链路。

---

## 一句话

> **检索是 9 阶段 pipeline:QUERY_UNDERSTAND(LLM改写query+意图分类)→CHUNK_SEARCH_PARALLEL(向量+关键词并发,RRF融合)→CHUNK_RERANK(cross-encoder两阶段精排+复合分+MMR)→CHUNK_MERGE(8步增厚:父子展开+邻居扩展+连续合并)→FILTER_TOP_K(截断)→INTO_CHAT_MESSAGE(结构化包装+短handle)→LLM。核心是"粗排求全+精排求准"两阶段,用 bi-encoder 快速捞一批再 cross-encoder 精挑。**

---

## 一、9 阶段 pipeline 骨架

用户问一个问题,不是直接搜,走流水线(chat_manage.go:320):

```
用户 Query
  ├─ 1. LOAD_HISTORY          载入历史(多轮才有)
  ├─ 2. MEMORY_RECALL         记忆召回(跨会话长期记忆)
  ├─ 3. QUERY_UNDERSTAND      ★LLM改写query + 意图分类
  ├─ 4. CHUNK_SEARCH_PARALLEL ★检索(chunk检索+图实体检索 并行)
  ├─ 5. CHUNK_RERANK          ★rerank重排(精排)
  ├─ 6. WEB_FETCH             (开了联网才有)
  ├─ 7. CHUNK_MERGE           ★合并(父子展开+邻居扩展+去重,8步)
  ├─ 8. FILTER_TOP_K          ★最终截断
  ├─ 9. INTO_CHAT_MESSAGE     组装成prompt
  └─ 10. CHAT_COMPLETION_STREAM 喂LLM流式生成
```

带 ★ 是检索核心。query 改写和意图分类在笔记 26 详讲,本篇重点 4/5/7/8。

## 三、CHUNK_SEARCH_PARALLEL:双路并行检索(核心)

### 3.1 双路并发

`CHUNK_SEARCH_PARALLEL`(search_parallel.go:90)并发跑两条:
```
CHUNK_SEARCH_PARALLEL
  ├─ chunk_search  → CHUNK_SEARCH  (向量+关键词混合检索)
  └─ entity_search → ENTITY_SEARCH (图实体检索,query_knowledge_graph那套)
合并 + removeDuplicateResults 去重 → chatManage.SearchResult
```

### 3.2 query 向量化:跟入库用同一个 embedding 模型(强约束)

检索前 query 变向量(knowledgebase_search.go:25 `GetQueryEmbedding`):
```go
embeddingModel := s.modelService.GetEmbeddingModel(ctx, kb.EmbeddingModelID)
return embeddingModel.Embed(ctx, queryText)   // 单条 embed
```
**query embedding 用的模型必须跟该KB入库时chunk embedding同一个**(都是 kb.EmbeddingModelID)。否则query向量和chunk向量不在同一向量空间,cosine相似度全是垃圾。多KB检索时 validateSameEmbeddingModel 校验所有KB模型一致。**query向量只算一次**(按模型分组,每组算一次透传)。

### 3.3 向量检索 vs 关键词检索:并发跑两条路

`HybridSearch` 内部 `CompositeRetrieveEngine.Retrieve`(composite.go:32)**并发**跑,每个一个 goroutine:

**向量检索**(postgres/repository.go:265 VectorRetrieve):
- pgvector,cosine距离 `embedding <=> $1`,HNSW索引加速
- 分数 = `(1 - distance)`(距离转相似度)
- **over-retrieval**:先多捞(top-K的5倍,下限100上限200),给rerank留余量
- MatchType = MatchTypeEmbedding

**关键词检索**(postgres/repository.go:164 KeywordsRetrieve):
- **ParadeDB** `|||` 操作符做BM25全文检索(不是原生to_tsvector)
- 分数 = `paradedb.score(id)`(BM25分)
- **不带embedding**(只有query文本)
- **FAQ KB永远不走关键词检索**(FAQ类型被排除)
- MatchType = MatchTypeKeywords

### 3.4 走哪条路由由 IndexingStrategy 决定

逐KB判断(knowledgebase_search.go:370-385):
- `kb.IsVectorEnabled() && EmbeddingModelID != ""` → 进向量池
- `kb.IsKeywordEnabled() && Type != FAQ` → 进关键词池
- 两者都开 → **hybrid**(同时构造向量params和关键词params,并发跑)
- query embedding失败 → DisableVectorMatch=true 降级纯关键词

### 3.5 混合检索融合:RRF(Reciprocal Rank Fusion)

向量结果和关键词结果怎么合并?**RRF融合**(knowledgebase_search_fusion.go:84 fuseWithRRF):
```
RRF分数 = vectorWeight/(k + vectorRank) + keywordWeight/(k + keywordRank)
默认: k=60, vectorWeight=0.7, keywordWeight=0.3
```

**为什么用RRF不用分数直接加**?向量分数(cosine相似度0~1)和关键词分数(BM25可能几十几百)**量纲完全不同**,直接加被BM25大数值淹没。RRF用**排名**(rank)不用原始分数——第1名rank=1,分数=权重/(k+rank)。**rank-based对量纲免疫**,这是RRF精髓。

**权重0.7/0.3**:向量结果占主导(语义检索更准),关键词结果补充(精确匹配术语)。同chunk被两路召回,按ChunkID合并取向量结果高分元数据。

### 3.6 粗排深度:over-retrieval(多捞再截)

向量检索默认top-50(EmbeddingTopK),实际多捞5倍(knowledgebase_search.go:162):
```go
matchCount = max(MatchCount*5, 50) * len(searchKBIDs)  // 上限500
```
为什么多捞?后面有rerank精排——粗排宁可多捞(top-250),让rerank从更大池子挑真正相关top-10。**粗排求全,精排求准**。两阶段检索核心思想。

## 四、CHUNK_RERANK:精排(核心)

粗排给top-50(实际更多),rerank挑出真正相关top-10。

### 4.1 rerank用专门cross-encoder模型,跟embedding模型不是同一个

**两个独立模型**(model.go:14):
- `ModelTypeEmbedding`:embedding模型,做向量检索(把文本压成向量)
- `ModelTypeRerank`:rerank模型,做精排(给query-doc对打相关性分)

rerank模型是**cross-encoder**类——把query和每个候选doc拼成一对,逐对打分(reranker.go:14 `Rerank(ctx, query, documents[])`)。项目根有 rerank_server_demo.py,用HuggingFace AutoModelForSequenceClassification跑独立rerank服务。

**为什么embedding不够要rerank**:embedding是**bi-encoder**(query和doc各自独立编码成向量再算距离),快但粗(query和doc没交互)。rerank是**cross-encoder**(query和doc拼一起进模型,逐token交互),慢但准。**先用bi-encoder粗排捞一批(快),再用cross-encoder精排挑准(慢)**——用速度换精度的两阶段。

### 4.2 租户级全局配置,不是知识库级

RetrievalConfig存租户表JSONB列(retrieval_config.go:14),一个租户配一个rerank模型对所有KB生效。RerankModelID为空跳过rerank。

### 4.3 输入输出

**输入**:`(RewriteQuery, 候选passages[])`。passages不是原始chunk content,是getEnrichedPassage清洗增强过——cleanPassageForRerank剥离markdown噪声(图片URL/表格分隔符/代码块),只留语义文本,合并图片caption/OCR/生成的问题。

**输出**:每个passage一个RelevanceScore(cross-encoder打分,sigmoid归一化0~1),按分降序。

### 4.4 复合打分:不只看rerank模型分

不直接用模型分排序,算**复合分**(rerank.go:439 compositeScore):
```
composite = 0.6×rerank模型分 + 0.3×向量检索分 + 0.1×来源权重
```
**60% rerank + 30% 原检索 + 10% 来源**。rerank占主导但不完全覆盖原检索信号——rerank模型可能误判,留30%原检索分兜底。web_search来源权重0.95(略低,联网内容可靠性不如知识库)。

### 4.5 阈值过滤 + 退化重试 + top-1兜底

- 先按RerankThreshold(默认0.2)过滤低分
- **阈值退化**(rerank.go:148):全被滤掉且原阈值>0.3 → 降到0.7×再试(下限0.3),避免阈值太高一个都没
- **top-1兜底**(rerank.go:394):退化后还全空但最高分≥0.15 → 保留top-1作安全网
- "宁可返回凑合的,别返回空"的工程兜底

### 4.6 MMR去冗余(最大边际相关性)

复合分排完序,MMR(rerank.go:458 applyMMR)做多样性去重:
```
MMR分数 = λ×相关性 - (1-λ)×冗余度
默认 λ=0.7
```
`相关性`=chunk复合分,`冗余度`=跟已选chunk的Jaccard文本相似度(jieba分词后算)。**70%看相关性,30%看跟已选是否重复**。top-10不会全是说同一件事的10个chunk,覆盖不同角度。

## 五、CHUNK_MERGE:合并增厚(8步,核心)

rerank给top-10,每条还是单独chunk。merge"增厚"——8步(merge.go:44):

```
PluginMerge.OnEvent (merge.go:44)
  Step1  selectInputResults     选输入(rerank结果优先,空则回退向量分排序)
  Step2  dedup                  初始去重(按chunkID+内容签名)
  Step3  injectHistoryResults    ★注入历史检索结果(Jaccard>0.15,score打6折,最多3条)
  Step4  resolveParentChunks     ★父子分块:子块拉父块拼上下文(笔记21/24摸的)
  Step5  groupAndMergeCurrentContent ★按KnowledgeID+ChunkType分组,合并连续chunk
  Step6  populateFAQAnswers     FAQ答案填充
  Step7  expandShortContextWithNeighbors ★短chunk(<350rune)拉前后邻居扩到≥350
  Step7.5 groupAndMergeCurrentContent 再合并(扩展可能引入新重叠)
  Step8  dedup + removePartialOverlaps 最终去重
  → chatManage.MergeResult
```

### 要点

**历史注入(Step3)在父子解析(Step4)之前**——历史引用先注入,跟当轮结果一起参与后续父子解析和合并。Jaccard相似度>0.15才注入,score打0.6折,最多3条。

**合并连续chunk(Step5)两条判断路径**(merge_overlap.go:129 classifyMerge):
- **trusted路径**(chunk没被编辑、没被改写、坐标有效):用StartAt/EndAt位置区间判断相邻/重叠/包含
- **untrusted路径**(编辑过/坐标失效):退回ChunkIndex==lastIndex+1(索引相邻)或文本包含

**为什么两条路径**:编辑过的chunk坐标可能失效,不能信任StartAt/EndAt,只能退回索引序。**绝不依赖可能失效的坐标**——merge的关键防御性设计。

**短chunk邻居扩展(Step7)**:内容<350rune的短chunk,沿PreChunkID/NextChunkID链拉前后邻居拼起来,扩到≥350rune,上限850rune。给LLM更完整上下文。

**关键顺序:merge在filter_top_k之前**。merge会**增加**条数(父子展开+邻居扩展),合并完再截断。短chunk扩展后仍作为一条参与TopK截断。

### resolveParentChunks(笔记21/24已详讲)

子块命中拉父块拼上下文。哪些ChunkType拉父:ChunkTypeText→ParentText(普通父子),ChunkTypeImageOCR/Caption→Text父→ParentText爷爷(图片三层)。父块用JoinChunkContent拼子块前,双换行分隔。image_info按durable URL scope到命中子块。

## 六、FILTER_TOP_K:最终截断

merge增厚后,按分数降序+多级tie-break(KnowledgeID/ChunkType/ChunkIndex/ID)排好,截到RerankTopK(默认10)条。

**关键:没有token budget裁剪**。grep全链路无按token预算动态裁剪检索结果逻辑。靠**条数TopK(10条)+每条扩展上限(850rune)**间接控制context量,不是精确token计数。LLM context超限风险靠这两个硬上限兜。

## 七、INTO_CHAT_MESSAGE:组装成prompt

把top-10检索结果包装进prompt喂LLM(into_chat_message.go:121):
```xml
<documents>
  <document><title>...</title><description>...</description><metadata>...</metadata></document>
</documents>
<context id="1">enriched passage 1</context>
<context id="2">enriched passage 2</context>
```

**结构化包装**:`<documents>`头(文档级信息)+每条`<context id="N">`包裹增强后passage。图片用getEnrichedPassageForChat富化——保留Markdown图片语法(让LLM能原样复制图片),后面追加`> **Image caption:** ...` OCR/caption文本。

### 引用怎么传LLM:短handle而非原始UUID

LLM看到的是`c1/c2/d1/b1`**短handle**,不是原始chunk UUID(references.go:60 RegisterSearchResults)。durable UUID压缩成request-local handle,LLM答案里复制handle,系统解码回真实ID。SubChunkID不直接传LLM,只在merge内部追溯用。system prompt末尾还会appendRetrievedImageOutputRequirement——检测到含图片追加图片输出要求。

## 八、完整链路一图流

```
用户 Query
  │
  ▼ QUERY_UNDERSTAND: LLM改写 → RewriteQuery + 意图(笔记26详讲)
  │
  ▼ CHUNK_SEARCH_PARALLEL(双路并行)
  │  chunk_search:
  │    query向量化(同入库embedding模型,每组算1次)
  │    → HybridSearch:
  │       向量检索(pgvector HNSW cosine, over-retrieve 5×50=250)  ┐
  │       关键词检索(ParadeDB BM25, FAQ不参与)                    ├并发
  │       → RRF融合(0.7/(60+vRank)+0.3/(60+kRank),量纲免疫)      ┘
  │    → chatManage.SearchResult (top-50)
  │  entity_search: 图实体检索(并行)
  │  合并去重
  │
  ▼ CHUNK_RERANK(精排, RerankModelID空则跳过)
  │  清洗passage(剥离markdown噪声)
  │  → rerank模型(cross-encoder逐对打分,sigmoid 0~1)
  │  阈值过滤(0.2) + 退化重试(×0.7) + top-1兜底(≥0.15)
  │  复合分 = 0.6×rerank + 0.3×检索分 + 0.1×来源
  │  MMR去冗余(λ=0.7, Jaccard, top-10)
  │  → chatManage.RerankResult
  │
  ▼ CHUNK_MERGE(合并增厚, 8步)
  │  去重 → 历史注入(Jaccard>0.15,6折,3条) → 父子展开(子拉父,图片三层)
  │  → 分组合并连续chunk(trusted用坐标/untrusted用ChunkIndex) → FAQ填充
  │  → 短chunk扩邻居(<350扩到≥350) → 再合并 → 最终去重
  │  → chatManage.MergeResult
  │
  ▼ FILTER_TOP_K: 截到RerankTopK(默认10),无token budget靠条数+每条850rune
  │
  ▼ INTO_CHAT_MESSAGE: <documents>头 + <context id=N>包裹 + 图片富化
  │  引用→短handle(cN/dN/bN),SubChunkID不进prompt
  │
  ▼ CHAT_COMPLETION_STREAM: 喂LLM流式生成答案
```

## 你应该带走的 7 个关键认知

1. **检索是9阶段pipeline**:QUERY_UNDERSTAND(query改写)→SEARCH_PARALLEL(双路检索)→RERANK(精排)→MERGE(合并增厚)→FILTER_TOP_K(截断)→INTO_CHAT_MESSAGE(组装)→LLM。resolveParentChunks只是MERGE里一个子步骤。

2. **query先被LLM改写**:用RewriteQuery不是原始query。检索质量第一道保障。详见笔记26。

3. **双路并行检索+RRF融合**:向量(pgvector cosine)和关键词(ParadeDB BM25)并发跑,RRF融合(用rank不用原始分数,量纲免疫,0.7向量+0.3关键词)。query embedding跟入库用同一个模型(强约束,不然向量空间不对)。

4. **两阶段检索:粗排求全+精排求准**。粗排over-retrieve 5×(top-250)用bi-encoder(embedding快但粗),精排rerank用cross-encoder(慢但准)从大池子挑top-10。用速度换精度经典两阶段。

5. **rerank独立模型(租户级),复合分不只看模型分**:0.6×rerank+0.3×检索+0.1×来源。rerank占主导但留30%原检索兜底。阈值退化重试+top-1兜底(宁可返回凑合的别返回空)。MMR(λ=0.7)去冗余保证top-10不全是重复内容。

6. **MERGE在FILTER_TOP_K之前(先增厚再截断)**:merge 8步会增加条数(父子展开+邻居扩展),合并完才截TopK。合并连续chunk有trusted(用坐标)/untrusted(用ChunkIndex)双路径,绝不依赖可能失效的坐标。短chunk<350rune拉邻居扩到≥350。

7. **无token budget裁剪**:靠条数TopK(10)+每条850rune上限间接控量。引用传LLM用短handle(cN/dN)非原始UUID,SubChunkID不进prompt。
